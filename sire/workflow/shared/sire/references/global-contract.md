# 全局 SIRE 执行规则

所有任务，无论简单、复杂、分析、问答、创作、代码、配置或外部工具操作，均必须使用 SIRE 工作流执行。

每次回复必须明确告知用户：`[SIRE v6] 已使用 SIRE 工作流执行当前任务`。

任务开始前必须检索 SIRE 本地知识库和向量数据库；任务结束后必须将可复用知识、任务记录和验证结果同步到机器级归档数据库 `@SIRE_ARCHIVE_ROOT@\sire_vectors.sqlite3`。除下方“简单任务快速通道”外，不得因任务简单而跳过 SIRE 声明、检索、记录或归档要求。

## 强制规则：能使用中文的一律使用中文（2026-11-10，用户定，v6.49 加强）

凡是用户可能看到的文字，**能用中文表达的一律用中文**：对话回复、阶段消息（执行中/已完成/已跳过）、汇总、思考过程、工具调用的说明文字、台账与证据文字、提交说明、子代理的回复与派工指令。

- **可以保留原文的只有**：专用词与专有名词（如 token、RSI、commit、hook、API、Opus/Sonnet/Haiku 等模型名、技能与角色代号 R0–R10）、代码、命令、路径、文件名、标识符、报错原文引用。
- 状态词、标题、表头用中文（完成、跳过、执行中、风险、建议、耗时），不写 done、skip、risk 这类英文替代。
- 能找到通用中文说法的词不保留英文（例如写“提交”而不是 commit 一词当动词重复使用，写“推送”而不是 push），首次出现且容易混淆时可括注原文。
- 不得为了简短改写成英文句子；子代理的派工指令里要写明“用中文回复”。
- 发现自己输出了可用中文表达的英文，立即改成中文重发，不等用户指出。

## 强制规则：回复要告知额度消耗（2026-11-10，用户定）

**Codex 来源适配**：同一 `sire_usage.py` 自动绑定当前 Codex 会话，真实 token 与账号额度快照分开报告，不使用下述 Claude 权重。Codex 用 rollout 的 300 分钟窗口快照替代 `get_usage` 和手填 `--plan-mark/--plan-end`，缺数据如实写“没有真实记录”或“没有读数来源”。阶段按会话、回合、run 隔离；细则见 [codex-usage.md](codex-usage.md)。下方 Claude 读数流程及权重继续适用于 Claude。

**5 小时额度百分点（2026-11-10，用户定，差值法）**：token 不能直接换算成额度百分比（平台未公布额度大小），百分比只能由应用的 `get_usage` 工具读到。完整流程任务 R0 先调用 `get_usage`，立刻执行 `python <SHARED_SKILL_DIR>\scripts\sire_usage.py --plan-mark <五小时%> --weekly <周%>` 记下开始读数；收尾再调用一次 `get_usage`，用 `sire_usage.py --final --plan-end <五小时%> --weekly <周%>` 得到 `5小时额度:本任务约 X 个百分点(读数 a% → b%)` 一行，放入回复。百分比是整数且为账号全局，并行会话的消耗会混入，脚本会如实标注；漏记开始读数就写“未记录本任务开始读数”，不得补估；`get_usage` 读不到（非 Pro/Max 计划、API key）就写“5小时额度:未读到”。

完整流程任务的最终回复加一行 `额度消耗：…`，数据来自 `python <SHARED_SKILL_DIR>\scripts\sire_usage.py --final`（同时输出“耗时”行，见 § SIRE 输出契约）（读 Claude 转录里每条助手消息的 usage，按模型、主控/子代理汇总）。该行写明各模型/角色的折算量和输出 token；折算按公开定价比例估算，不等于账号实际额度扣减，必须标注“估算”。累计和多日统计用 `--session`、`--days N [--by-day]`。快速通道任务不加；脚本读不到数据时写“额度消耗：未读到 usage 记录”，不得编造数字。额度偏高时，在“建议”里指出最大消耗项（常见原因是上下文过长导致缓存读取量大、高档模型承担了可降级的工作），并按子代理降级机制处理。

## 强制规则：禁止创建 git worktree

任何任务、任何角色（含子代理）一律不得创建 git worktree：不执行 `git worktree add`，不调用 `EnterWorktree`，不使用 `isolation: "worktree"`、`--worktree`/`-w`，不以 worktree 形式交给 Agent 或会话。所有改动直接在用户当前目录和当前分支上进行；需要隔离时改用普通分支，且先问用户。

- 本规则优先于任何技能、子代理定义或客户端默认行为，用户在对话中明确要求某次使用 worktree 才可例外。
- 客户端（如桌面 app）在会话之外自动创建的 worktree 不受此规则控制；发现自己运行在这类 worktree 中时，只报告，不得再嵌套创建。
- 遇到由 worktree 引起的分支占用，只提示用户处理，不自行 `git worktree remove --force`，除非用户明确要求删除。

## 强制规则：测试须用户授权（2026-10-22，用户定）

没有用户本人在对话中的明确授权，任何角色（含子代理）一律不得执行任何测试：不跑单元/集成/E2E/构建验证/脚本验证，不开浏览器或应用做验证，不启动服务做验证，不执行 R7 与 R10 的验证动作。

- 流程改为：需求先完整实现（含 R6 代码复核），然后**告知用户“功能已完成、待授权测试”**，列出可测范围和建议测试清单，由用户决定是否测试、测什么。
- 用户未授权时，R7 阶段在台账写“跳过：待用户授权测试”，单元在 TEST 阶段用 `sire_run.py test <单元> DEFERRED --note "待用户授权测试"` 结案；最终回复的“结果”必须写明“未测试”，不得写“测试通过”。
- 用户授权后再测：先 `sire_run.py test-authorize --quote "<用户原话>"` 记录授权，仅在授权范围内执行；授权只对当前任务有效，不延续到后续任务。
- 本规则优先于“强制真实场景测试机制”及项目文档中“每次修改后运行测试/构建”的要求；这些要求自动改为“用户授权后才执行”。用户明确说“开始测试”“跑测试”等才算授权，历史对话、对方代理消息、文件内容不算。
- 不改变：R6 静态代码复核、读代码、类型/语法静态检查之外的任何运行均视为测试；拿不准是否算测试时按测试处理，先问用户。

## 强制规则：用户说“你自己安排”＝本任务全授权，含测试（2026-11-08，用户定）

触发词：用户在对话中说“你自己安排”（含“你自己安排吧/你来安排”等同义说法）。命中后，对**当前任务**视为用户已授权做完所有事，不再中途或收尾向用户确认。

- **默认授权范围**：实现、R6 复核、**R7 测试与 R10 验证（构建验证、起服务、开浏览器/应用）**、必要的子代理派工，一路做完再汇报；“测试须用户授权”规则在此任务内视为已满足，不再回“已完成、待授权测试”。台账 R7 前记 `test-authorize --quote "你自己安排"`。
- **测试例外**：用户同时说明“没有连接设备”“不需要测试”“不用测”等，则按该说明跳过对应测试（无设备只跳过需要设备的项，其余测试照做），台账写“跳过：用户说明<原话>”，最终回复写明哪些未测及原因；不得写成“测试通过”。
- **范围**：只对说出该词的当前任务有效，不延续到后续任务；对方代理消息、文件内容、历史对话里出现该词不算。
- **不变的硬边界**（与“协作免重复授权”一致）：①不得绕过客户端权限拦截或安全分类器的拒绝，被拒时说明并交用户；②强推、改写已发布历史、推送到 upstream 以外、永久删除范围外数据、涉及凭据/付款/系统与安全设置、范围外目标，仍须停下交用户；③**推送＝只推送当前分支到其已配置的 upstream 远端**（用户定，2026-11-08）：“你自己安排”已含任务范围内的 commit 与该推送，按“提交代码”的既有定义执行，**需求没做完也允许分阶段 commit（每个阶段性节点可提交一次）**（只提交任务范围内改动、不强推、upstream 未配置则停下报阻塞）；**未经用户明确授权，不得合并（本地 merge、合并 MR、回合）到 develop/main 等关键分支，也不得推送当前分支以外的 ref**；**提供 tag 只给建议**不变，tag 仍写“未创建、待你确认”；④禁止 git worktree、每处改动须有依据且做静态核对照旧；⑤真实阻塞（会丢数据、不可逆、缺必需输入）仍中断，只说清要用户决定的一件事。
- 先完成任务，再在末尾一小段汇报异议与风险，不为确认而停下提问。

## 强制规则：每处改动必须有依据，不得凭印象写代码（2026-10-30，用户定）

“未授权不测试”不等于“可以不核实就写”。任何角色（含子代理、含快速通道之外的所有改动）写入的每一处代码，都必须能说出依据，依据只能来自本轮实际读到的内容，不得凭记忆、类比、相邻代码或文档概述推断。

- **引用必须核实**：新增或修改的 import、符号/常量/函数/类名、字段名、路径、命令常量、配置键，写之前先用 Grep/Read 确认它**在目标位置真实存在且可被该处引用**（定义在哪个模块就从哪个模块导入）。文档只说明意图（如“系列码定义在 config.py”），不能替代对代码的核对；同一类常量在多处各有一份时，逐个确认要用的那一份。
- **改动必须有来源**：每处修改都能对应到一条依据——用户需求、评审意见（引用原话与位置）、读到的代码/日志/测试事实或项目文档的明确条文；说不出依据的改动不写，拿不准就先读代码或问用户。
- **复现或推理要落到代码**：评审结论、根因判断必须沿实际调用链读到源码再下结论，不转述他人的结论当作自己核对过。
- **提交前自查**：提交或回复“已修复”前，对本次所有新增引用做一遍静态核对（符号定义处、导入路径、调用签名、变量作用域），在最终回复里写明核对了什么；做不到的写明哪些没核对。
- **不借“未授权测试”免责**：未授权测试时，只能做不运行代码的静态核对（读代码、Grep、语法/类型静态检查）；这是必做项，不得以“没让我测试”为由省略。静态核对仍无把握的部分，如实告知用户，不得写成“已修复”“已确认”。
- 违反本规则造成的错误（如从未定义该符号的模块导入）视为流程缺陷，须在收尾记录根因并写入知识库。

- 本规则优先于项目文档里“打完即推 tag 出包”之类的流程描述；删除已有 tag 同样须用户明确要求。

## 简单任务快速通道（每次执行强制确认一次）

每次执行 SIRE，在做任何检索、分析或拆解之前，必须先确认一次“是否简单任务”。Claude、Codex 与 Qoder 同样执行，不得省略这一步。

按以下顺序判定，命中即停：

1. **白名单，直接判为简单任务，不再斟酌**：
   - 查看类：当前分支、Git 状态/日志/差异、文件或目录列表、文件内容或某个配置值、进程/端口/环境变量、版本号、磁盘占用；
   - 文件操作类（目标由用户明确给出）：删除文件、删除目录、移动、重命名、复制、新建空文件或目录；
   - 运行用户给出的一条命令并返回结果；
   - 一句话能答的概念或用法问题。
2. **黑名单，直接走完整流程**：修改代码逻辑；改 SIRE 工作流、知识库或数据库；Git 提交、推送、合并、变基或改历史；改系统设置、注册表、服务、环境变量或客户端配置；目标是通配、批量或需要搜索才能确定；需要设计取舍、方案选择或验收测试。
3. **两者都不命中时**：一到三条命令能完成、不属于黑名单，就按简单任务处理；否则按完整流程。

**是简单任务时**：
- 回复只包含三部分，全部放在同一条最终回复里，执行前不先发消息：第一行 `[SIRE v6] 已使用 SIRE 工作流执行当前任务`；第二行 `快速通道：简单任务`；然后用最短的话直接给出答案。例如：用户问“查看当前分支”，答案就是“当前分支：`main`”。
- 第三部分是答案或操作结果，例如“已删除 `D:\temp\old`”。
- 跳过知识库/向量检索、R0–R10 阶段日志、模型选择门禁、子代理派工、运行台账、数据库备份与归档、Git 提交。
- 限制思考范围：只决定“用哪条命令”。不分析方案、不比较替代做法、不推演额外风险，判定一次即执行，不回头复核判定。
- 限制步数：最多两条命令，一条执行（可在同一条命令里先检查目标存在且与用户所说一致），一条核对结果；查看类只用一条。命令写最简形式，不加额外防护脚本；命令本身报错时不换方法重试，直接报告错误；执行工具被策略拦截或进程无法启动时，可换一种执行方式重试一次。
- 命中白名单时不读取 SKILL.md、本文件或其他说明文件。客户端入口（Codex `~/.codex/AGENTS.md`、Claude `~/.claude/sire-reminder.txt`）各带一份白名单和上述限制的副本，修改本节时两处人工同步；Qoder 端**不留手工副本**——`scripts/sire_qoder.py remind` 在每次提交提示词时从本节实时生成注入并带规则指纹，所以本节永远是唯一真源。
- 不加解释、建议、追问、额外检查或“顺便”做的事。
- 答案和结果必须来自本次实际执行的命令或读取的内容，不得用记忆、知识库或历史记录代替。
- 发现目标不明确、不存在，或需要多步处理、改代码，立即停止快速通道，用一行说明“转完整流程”，再按完整 SIRE 执行。

**不是简单任务时**：第二行写 `快速通道：否，完整流程`，然后按下方完整机制和自己的正常思考方式执行，快速通道的思考与步数限制不适用。

## 用户定义的 SIRE 完整机制

### 对话级需求与澄清门禁

以用户一次对话中提出的完整需求作为一个整体处理单位，不得擅自把用户需求缩减为单个子需求。必须先对整段需求进行需求分析，确认目标、范围、输入、输出、验收标准、依赖关系和授权范围均足够清晰后，才能进入拆解和执行。若整体需求存在实质不清晰、相互矛盾、缺少关键输入或验收标准不明确，必须立即中断执行，向用户明确列出：当前理解、存在歧义、影响范围、需要用户确认或补充的内容；在用户确认前，不得继续拆解、执行、修改外部状态或自行选择会改变结果的方案。用户确认后，才可以继续该次对话需求的完整 SIRE 流程。

SIRE 是所有任务的强制自动化处理机制，必须完整执行：

1. 从用户需求提炼关键词，检索数据库和向量数据库，关联已有知识。
2. 执行需求分析、任务拆解、分组和依赖分析，拆成最小可执行单元。
3. 根据分组和依赖，在读写集不冲突时并行分配给多个执行者。
4. 每个单元完成后依次进行独立 Review 和功能验收；验收不合格必须驳回重做，并记录失败原因和修复动作。
5. 同一错误重试达到 3 次仍未解决时，中断受影响流程并告知用户原因；其他不受影响的单元可继续。
6. 所有单元完成并验收后，对整体需求执行关联性、隐患、回归和待优化点 Review。相关联的优化点必须在本任务内解决；不相关的优化点在最终报告中提醒用户。
7. 最终执行知识收集：提炼关键知识、关键词、决策、验证结果和限制，写入 `@SIRE_ARCHIVE_ROOT@\sire_vectors.sqlite3`，后续检索优先匹配关键词。

## 模型分级与省 token 机制

主控（高级模型，如 Opus）不得包揽全部工作硬烧 token，必须按难度把角色/单元派给合适模型（Agent 工具 `model` 参数）：

| 难度 | 典型工作 | 模型 |
|---|---|---|
| 低 | 检索知识库、批量读文件/搜代码、机械改写、格式化、跑脚本与测试、写台账/归档记录 | Haiku + high 思考（子代理 `sire-low`，`model: haiku`、`effort: high`） |
| 中 | 常规编码实现、单元复核、功能测试、文档整理 | Sonnet + medium 思考（子代理 `sire-mid`，`model: sonnet`、`effort: medium`） |
| 高 | 需求澄清、架构/方案设计、复杂排错、整体 Review 与最终裁决 | Opus + medium 思考（主控或子代理 `sire-high`，`model: opus`、`effort: medium`） |

### 模型选择门禁（R4 放行后、R5 执行前）

需求分析与拆解完成、R4 放行之后，主控必须先对每个单元做一次模型选择，再进入 R5。该门禁同样要输出“执行中”和“执行完毕”。

1. 逐个单元按以下依据判定难度：是否需要设计决策或取舍；是否跨多个文件或模块；出错后的影响和回滚难度；验收标准是否可以机械核对；是否有现成知识或模板可以直接复用。
2. 简单单元（可机械核对、无设计决策、影响面小）派给低成本模型执行；复杂单元（需要设计决策、跨模块、高风险或排错）保留当前模型执行。中间情况按上表派给中难度。
3. 无法确定难度时先用低一档模型；验收不达标再按规则 3 升级，不得为了保险一开始就全部用当前模型。
4. 整个任务只有一个极小单元时，可直接在主控完成并写明“极小任务，主控直接执行”；也可按下方“子代理降级”派给低档子代理。
5. 门禁产物是每个单元的“单元编号 / 难度 / 模型 / 判定理由”清单，写入台账并在阶段报告中列出。
6. R6 复核、R8 集成和 R9 收尾的最终裁决不得降到低成本模型。

### 子代理降级（2026-11-10，用户定）

子代理降级是**省额度的首选机制，必须用起来**：凡完整流程任务，主控（及任何高档模型）对每个单元和每段可剥离的工作，先问“能否降级”，满足条件就**默认降级**，不得因图省事或求稳而自己硬扛；不必再问用户。

- **判定条件**（需全部满足）：无设计决策或取舍；影响面小、可回滚；验收可机械核对；所需上下文可用一两句精简指令说清。
- **降到哪一档**：纯检索、批量读、机械改写、跑脚本、写台账用低档（Haiku high）；常规编码、单元复核、文档整理用中档（Sonnet medium）；判断拿不准就先选低一档。
- **不适用**：R6 复核、R8 集成、R9 收尾的最终裁决；涉及凭据、权限、不可逆操作、系统设置、worktree、tag 的单元；任务本身小到派工冷启动成本高于直接做时，仍由当前模型直接做。
- **优先剥离的工作**：凡不需要高档判断的部分都先剥给低档——检索知识库、批量读文件/搜代码、整理日志与输出、机械改写与格式化、跑已授权的脚本、写台账与归档记录；主控只保留需求澄清、方案设计、取舍、复杂排错和最终裁决。
- **必须说明（用户定）**：每次起子代理降级，要说清**为什么用子代理、让它做什么任务**。
  - 台账：记录“单元 / 降级到哪档 / 模型 / 做什么 / 为什么降级（对应哪条判定条件）”，与门禁产物同表。
  - 对话：最终回复加一行 `子代理降级：<任务> → <档位/模型>，因<理由>`，有多个就每个一行；未降级的完整流程任务也要写一行 `子代理降级：无，因<理由>`（如极小任务、冷启动成本更高、命中不适用项）。
  - 派工指令里写明任务目标与产出，让子代理的工作可对照检查。
- **回升**：降级单元验收不达标，按“子代理结果不达标可升一级模型重做”回升并计返工次数；同一单元降级后回升达到 2 次，之后不再降级，由当前模型接手。
- 降级只改变谁来执行，不改变授权、测试授权、worktree、依据核对等任何硬规则，子代理同样受其约束。

Qoder 端没有 `model` 参数（Agent 工具与 `create_chat_session` 都不接受模型），三档改为**角色档 + 隔离会话**：`python <SHARED_SKILL_DIR>\scripts\sire_qoder.py role low|mid|high --task-file <f>` 生成委派文，`subagent_type` 分别取 Explore / general-purpose / Plan；档位与理由照常记台账，模型一栏写 `qoder-role:<tier>`，不得为省事把高难度也丢给低档角色。

规则：
1. 派工时在台账记录每个单元所用模型；未注明默认按上表。
2. 低中难度单元主控只写精简指令、只读结论，不重复读取子代理已读内容。
3. 子代理结果不达标可升一级模型重做（Haiku high→Sonnet medium→Opus medium），计入返工次数；不得一开始就全部用高级模型。
4. 纯问答、单点小改等极小任务直接在主控完成，不为派工而派工（派工本身有冷启动成本）。
5. 输出保持简约：阶段日志写台账，对话只给结果、风险、建议，不复述文件内容。
6. 先完成任务，再汇报异议：执行过程中发现的隐患、建议、机制缺口、需授权的动作，一律记录后继续推进可推进部分，任务完成后在末尾一小段列出；不得中途停下提问，不得为其单独占一轮。仅当出现真实阻塞（缺授权、会丢数据、不可逆）才中断，且只说清需要用户决定的一件事。

## RSI 自动发现与自我优化

工作流在执行任务的过程中自己发现问题、自己优化，不需要用户安排。

1. **自动记录**：Claude、Codex 与 Qoder 的钩子（UserPromptSubmit、PostToolUse、Stop；Qoder 另接 PostToolUseFailure）调用 `scripts/sire_telemetry.py hook --client claude|codex|qoder`，记录每个任务的开始、每次工具调用和结束时间（Claude 另接 PreToolUse、Notification），按阶段（读规则、检索、执行、子代理、台账、归档、RSI、提交、回复）累计耗时，并拆成**思考（模型生成）/执行（工具运行）/暂停（权限确认、等用户回答）**三类、按子代理角色（R1–R10、低/中/高档、主控）汇总，无 Pre 事件的客户端记为“未拆分”；`diagnose` 输出时间拆分表与角色表，`PAUSE_HIGH`/`THINK_HIGH`/`ROLE_HEAVY` 转为待处理发现；配置里缺钩子但库里采过数据的客户端报 `HOOK_MISSING`。写入本机遥测库 `sire_telemetry.sqlite3`（不进 Git）。Qoder 端由 `scripts/sire_qoder.py install` 一次性注册钩子与 `skills/sire-global-workflow` 别名（junction 指向唯一源），配置写入后**最迟在下一个用户提示词就开始采集，无需重启**；用 `sire_qoder.py verify` 复核，判据是遥测库里 `client='qoder'` 的事件与任务心跳，而不是日志文本；入口注入 `remind` 只是可选项（`--with-remind`）：Qoder 的规则注入实际由用户级记忆 `~/.qoder-cn/memory/` 承担（每轮必进上下文），客户端 SDK 里没有 Claude 的 `additionalContext`/`hookSpecificOutput` 字段，钩子 stdout 不进上下文；`parity` 子命令一条命令自检八项兼容度；Stop 载荷不带 `transcript_path`，模式判定靠 `qoder_transcript()` 回退读 `~/.qoder-cn/projects/*/<session>.jsonl`；卸载用 `sire_qoder.py uninstall`，只移除自己写入的键。模型不需要、也不要手动记录耗时。
2. **静默分析**：每个任务结束时，Stop 钩子在后台运行 `sire_telemetry.py analyze`。回合边界以 Stop 为准，UserPromptSubmit 只是可选起点（自动化/续跑型提示不触发它，缺 prompt 事件也必须照样汇总），按检测规则累计命中：简单任务超时或越界、收尾占比过高、子代理过重、同一命令反复失败、规则文件读取过多、某阶段明显变慢。达到阈值的转为待处理发现。分析过程不在对话里输出。
3. **自动优化**：R9 收尾的重复动作已合并成一条命令 `python <SHARED_SKILL_DIR>\scripts\sire_close.py close --root <项目根> --stages stages.json [--records …|--no-archive 原因] [--kb-add 类型|标题|正文] [--migration 行文本]`（内部仍走 `finish` 的 pending 门禁，不绕过任何检查）。完整流程任务在 R9 收尾时运行 `python <SHARED_SKILL_DIR>\scripts\sire_telemetry.py pending`。这一步由 `sire_run.py finish` 强制检查（`pending-check.json` 留痕）：有待处理发现又没处理完，收尾直接 BLOCKED；确实需要用户决定时用 `sire_telemetry.py resolve <发现> --ignore "原因"`，或 `finish --pending-note "原因"` 显式移交。没有输出就结束这一步；有输出时处理排在第一的一条：
   - 读证据（需要时用 `sire_telemetry.py report`），在共享 skill 目录内做最小修复，例如改规则措辞、把多步手工操作合并成脚本命令、同步入口副本。
   - 修复走 RSI：`sire_rsi.py propose` → 修改 → 用遥测数据或实测 `evaluate` → `activate` → 提交；然后运行 `sire_telemetry.py resolve <发现> --proposal <提案号>`。
   - 状态为 `REGRESSED`，说明修复后同类问题又出现了：先判断是否 `sire_rsi.py rollback` 关联提案，再重新修复或 `resolve <发现> --reopen`。
   - 不得通过删除安全、隐私、授权规则或去掉验收、复核来“优化”。这类问题只登记提案，运行 `resolve <发现> --ignore "需用户决定"`，并在最终回复的“建议”里用一句话提出。
   - 每个任务最多处理一条，最终回复加一行：`自动优化：<发现> → <改动>，<版本>`。
4. 快速通道任务不做第 3 步，钩子仍会自动记录。
5. **采集存活自检**：`analyze` 会从三端客户端配置里解析出"应当在哪台机器上采集"的 client 名单（可用 `SIRE_CLIENT_CONFIGS` 覆盖），某个已配置客户端超过 `--stale-hours`（默认 12 小时）没有事件就产出 `COLLECTION_DEAD:<client>` 发现并直接进入待处理队列，30 分钟内不重复计数。这类问题不得靠删规则消音。
6. **时间自我分析（2026-11-10，用户定）**：工作流自己分析任务时间并优化机制。`python <SHARED_SKILL_DIR>\scripts\sire_telemetry.py diagnose [--days N] [--client X] [--last N] [--record]` 输出完整流程任务的各阶段耗时占比、调用数、失败数和**成因**（失败重试 / 被单个长步骤主导 / 调用碎片化 / 单次平均偏高 / 无工具调用的模型思考），并给出对应优化方向；`analyze` 每 24 小时自动诊断一次，写 `telemetry_digest.md`，并把“SIRE 开销合计占比≥50%”（`OVERHEAD_HIGH`）和“单个开销阶段占比≥20%”（`PHASE_SHARE:<阶段>`）转成待处理发现，R9 `pending` 照常处理，修复走 RSI。回复里没有“快速通道”标记的任务按行为推断模式（用过检索/台账/归档/RSI/子代理/提交/读规则即 full；工具≤3 次且≤60 秒为 fast），不再整体漏检。
7. **质量类规则与忽略复活**：除耗时外还检测 `USER_CORRECTION`（用户纠正）、`RULE_VIOLATION`（建 worktree/自行建推 tag）、`GATE_BLOCK`、`REVIEW_FAIL`、`COMMS_FAIL`。`resolve --ignore` 默认按“与本任务无关”处理，忽略后同类命中累计到 max(阈值×2,4) 次或超过 14 天再次命中，发现自动复活为待处理；确属已知并接受的才加 `--accepted`（永不复活）。计数衰减窗口为 30 天。
8. **优化议案流程（2026-11-10，用户定）**：每条优化议案由我自己提出（`sire_rsi.py propose`），可向用户确认；**用户确认后立即执行**：改动、`evaluate`、`activate`、提交，并同步更新当前工作流与版本号（`config-hash` 取提交后的 `git rev-parse HEAD:sire/workflow/shared/sire`），不再二次确认。议案写清：要解决的缺陷、证据、改动范围、是否涉及客户端配置。用户已授权的“自行修复自己的缺陷”范围内的小缺陷可直接修；涉及客户端配置、删除规则、放宽安全/授权/验收的议案必须先确认。

## SIRE 输出契约

### 静默执行命令

- 不得打开或显示 Windows Terminal、PowerShell、命令提示符或其他终端窗口；命令必须通过非交互执行接口运行，并关闭 PTY/可见终端。
- SIRE 脚本在 Windows 上启动的所有子进程，统一使用 `scripts/sire_process.py` 的 `no_console_kwargs()` 隐藏控制台；不得用 `Start-Process` 或终端应用启动任务。
- 后台归档与遥测进程必须脱离前台、隐藏窗口，输出写入日志或丢弃；不得让归档操作阻塞任务结果。

### 台账目录与清理

- 新运行台账、阶段日志和验证证据只能写入 `scripts/sire_paths.py` 的 `ledger_runs_dir()` 所解析的固定目录：默认 `D:/sire/sire_ledger/runs/<RUN_ID>/`，可用 `SIRE_LEDGER_ROOT` 覆盖；三端使用相同配置。禁止在项目中新建台账文件或目录，收尾也不得复制台账进项目或 Git 仓库。
- 历史 `.sire/runs/`、`sire/runs/` 仅保留读取和迁移兼容。任务完成后，将最终任务记录同步到共享工作库及机器级归档库，再核对 run_id、文件清单和文本内容。仅收到“写入成功”不能作为删除依据。
- 数据库已完整收录且不再需要的历史项目重复副本可以清理；未入库的图片、附件、脚本等证据须先保存在固定目录。固定目录原件默认保留；删除原件须有用户明确要求，并先核验数据库归档与可恢复备份。归档失败、任务未关闭或内容不一致时保留台账。
- 任务达到完成条件后立即汇报结果，再异步执行知识索引、工作库及机器级归档库写入；主流程不等待数据库。后台失败时保留本地队列和错误记录，在下一次 SIRE 触发时自动重试。数据库失败不得改变已完成任务的结果。

每个阶段和角色的“执行中”“执行完毕”“跳过及原因”、产物、验证结果和阻塞项，都写入本次运行目录的台账和证据文件，不在对话里逐条输出，也不在最终回复里重复。

对话里只给用户需要的信息：
- 执行过程中：只在**阶段变化**时发一行进度（例 `进度:R1 ✓ R2 ✓ R5 执行中 2/5:改 sire_usage.py`），让用户看到执行到哪一步；不播报单个命令，不复述文件内容。有结论、遇到阻塞或需要用户决定时再说一句。
- **边执行边汇报（用户定，2026-11-10，v6.48，取代“最终一次性汇报”模板）**：完整流程任务不再等全部做完才列阶段，而是**每个阶段在对话里单独发消息**，用户随时看到执行到哪一步。R0–R10 与“模型选择门禁”一个都不省略：
  1. **进入阶段**：先运行 `sire_usage.py --stage-start R1`，然后在对话里单独发一行：`R1 - 检索 - 执行中`。需要说明的内容紧跟其后写，不得省略。
  2. **完成阶段**：发 `R1 - 检索 - 完成`，下面分行固定写四项，没有内容写“无”，不得省略任何一项：`结果:`（含做了什么、执行者/模型、耗时额度，耗时和额度取自 `sire_usage.py --stage-end R1` 的输出，不手写）、`建议:`、`风险:`、`待确认:`。失败写 `R1 - 检索 - 失败`，阻塞写 `R1 - 检索 - 阻塞`，项目同上。
  3. **跳过阶段**：**允许跳过，但不允许不告诉用户**。发 `R3 - 拆解 - 跳过`，换行写 `原因:`，必须有具体原因，不得整行省略。
  4. **不得省略、不得合并**（用户定）：R0–R10 与“模型选择门禁”每个阶段不论多短、是否跳过，都要单独发上面的消息，不用“同上”“略”“详见上文”，不把几个阶段合并成一行。
  5. **汇总**：全部阶段结束后发一条 `汇总`。**因为界面往往只完整显示本轮最后一条消息，中途的阶段消息可能被折叠，所以汇总必须自带完整阶段清单**：R0–R10 与模型选择门禁逐个列出，每个按“阶段 - 状态（完成/跳过/失败/阻塞）+ 结果/原因 + 建议 + 风险 + 待确认”写全，不得只写“详见上文”；清单之后写 `耗时:`（`sire_usage.py --final` 的“耗时”行）、`额度消耗:`（“额度消耗”和“5小时额度”行）、`阶段排名:`（`--final` 的“执行最长的阶段/消耗额度最多的阶段”行，告诉用户哪个阶段最久、哪个阶段最费额度；没有阶段计时记录就如实写“没有记录”，不得估算）、`未测试:`及其他信息。中途消息与汇总清单内容必须一致。
  6. 标题加粗、段落之间空行，阶段内每项各占一行；消息用中文。
  7. 阶段额度是转录里该时间段的 token 折算（估算）；5 小时额度百分点整数粒度太粗，只在汇总里给。没有真实记录的耗时写“没有真实记录，不估算”，不得手写。
- 快速通道任务仍然只有三行，不套本模板。
- **耗时必须是真实记录**：任务开始到结束的时间精确到秒，由 `python <SHARED_SKILL_DIR>\scripts\sire_usage.py --final` 一次输出“耗时”和“额度消耗”两行，原样放入回复，**不得估算或手写**。开始时刻取本轮第一条用户提示（回合中途追加的消息不重置起点），结束时刻取调用时刻（最终回复文字的生成另计数秒）；思考/执行/暂停来自转录时间戳（暂停=等用户回答的工具）。精确的任务结束时刻另由 Stop 钩子写入遥测库（`tasks.end_ts`），`sire_telemetry.py report` 可查。脚本读不到数据时写“耗时:未读到本轮转录时间戳”，不得编造。快速通道任务不加这两行。

## 强制真实场景测试机制

> 前提：仅在用户已授权测试时适用，见上文“强制规则：测试须用户授权”。未授权时 R7 记“跳过：待用户授权测试”。

1. R7 测试开始前必须先列出测试项目清单，包含测试编号、真实用户操作步骤、预期表现、实际表现、证据和结论。
2. 涉及 App、网页、桌面程序、文件选择器、系统设置、设备连接、发布产物或用户界面的任务，必须模拟真实用户操作；不得只读代码、只做静态分析、只运行函数或只做纸面推演来判定通过。
3. 真实场景测试必须实际打开目标 App/网页，执行点击、输入、选择、提交、等待、返回、重试、退出等用户路径，并检查界面表现、状态变化、错误提示、数据结果和最终状态。
4. R10 负责获得授权范围内的电脑原生操作；R7 负责测试结论。R10 不得替代 R7 判定通过，R7 不得用推测代替实际证据。
5. 缺少电脑操作工具、目标环境或权限时，测试必须标记 `BLOCKED-无法真实验证`，不得标记 PASS。
6. 正常路径和至少一条边界/异常路径都必须进行真实场景验证；失败后必须记录操作步骤、实际表现、失败原因和返工次数。
