## 2. 第 2 步 · 把改动合进 develop（子先父后）【已验证】

**为什么必须子先父后**：主仓锁的是子模块的提交指针；主仓合进 `develop` 时 git 不检查指针是否可达，指针指向的提交若还不在子仓 `develop` 上，将来重建会失败，而且没有任何报错（`docs/branching.md`）。

### 2.1 现状核对（只读）

```bash
cd D:\code\EncoderPlotter_0903_01
git fetch --all --prune
git branch --show-current
git rev-list --left-right --count origin/develop...HEAD        # 左=develop 多，右=本分支多
git status --short                                             # 有无未跟踪/未提交文件（有就不要动、不要提交）
git merge-tree --write-tree origin/develop HEAD                # 退出码 0 = 合并预演无冲突
git diff --raw origin/develop...HEAD | grep 160000             # 哪几个子模块指针变了
```

对**每个变了的自有子仓**（sub_common / sub_embedded / sub_automation）核对指针是否已在该子仓 develop 上：

```bash
cd controller/python/sub_common    # 其他子仓同理
SHA=$(git -C ../../.. rev-parse HEAD:controller/python/sub_common)
git fetch -q origin
git merge-base --is-ancestor $SHA origin/develop && echo 可达 || echo 不可达
```

`sub_algorithm` 是**例外**（算法部门自定形态，不加分支保护、不纳入门禁）：不要求在 main 上，但必须被**某个**远端分支或 tag 包含，否则就是悬空：

```bash
git -C controller/python/sub_algorithm fetch -q --prune origin '+refs/heads/*:refs/remotes/origin/*' '+refs/tags/*:refs/remotes/origin-tags/*'
git -C controller/python/sub_algorithm for-each-ref --contains <gitlink> --format='%(refname:short)' refs/remotes/origin refs/remotes/origin-tags
```

结果为空必须停发。非空就把"所在远端引用"写进记录（4.12.0 是只在 `origin/feature/algoV4000`），**发版 MR 里再贴一次**。

还要看有没有**别人的**、改了相同文件的已开 MR（GitLab 页面或 `GET /api/v4/projects/software%2FEncoderPlotter/merge_requests?state=opened`）。4.12.0 时有 !126（高星 9 月提），与我们改了 5 个相同文件。**别人的 MR 不合、不评审、不分析**，汇报里提示一句即可。

### 2.2 按顺序提 MR（每个仓库一个，同名分支 → develop）

顺序：`sub_common` → `sub_embedded`（若引用了 sub_common 的新东西，必须在它之后）→ `sub_automation`（仓库 `factory-automation`）→ **主仓最后**。

提 MR 用 GitLab 内网页面的"新建合并请求"：
`http://192.168.1.200:8888/software/<仓库>/-/merge_requests/new?merge_request[source_branch]=<分支>&merge_request[target_branch]=develop`

- 标题、描述写人话；表单会自动带"最后一个提交"的标题和描述，要**替换**。
- 描述里写清：是什么、提交清单、**合并顺序与依赖**、合并要求（merge commit，不要 squash）、没做的（没跑测试）。主仓 MR 要写四个指针的值与可达性、别人 MR 的冲突提示。
- **取消勾选"合并后删除源分支"**：这条分支是周更新工作分支，四个仓库同名共用，删了不可逆。
- 不 squash、不 rebase 合并（保留 merge commit）。

### 2.3 逐个 MR：评审 → 记录 → 修复 → 再审 → 合并

对每个 MR 循环，直到评审结论是"可以合并"：

1. **评审**（静态，读 `git diff origin/develop...HEAD`；**不跑测试**）。看：行为正确性、安全与边界（会写设备的路径：标定、设零、IAP、改参数）、工程质量与回归（`AGENTS.md` 规则，例如产品系列码以 `sub_common/config.py` 为唯一来源）、子仓之间接口对得上。主仓还要核对：**CHANGELOG 条目与提交**、四个指针与子仓一致。
2. **评审记录**（一个 MR 一份文件），格式固定：

   ```markdown
   ## Review 记录（第 N 轮）
   **结论**：可以合并 / 有条件通过（见 P1）/ 需要修改后再审
   范围：…；源提交：…；评审基线：…
   | 级别 | 位置（文件:行 或 提交） | 问题 | 建议 |
   | --- | --- | --- | --- |
   | P0 | … 会造成错误行为或数据损坏 | … | … |
   | P1 | … 应在合并前修 | … | … |
   | P2 | … 可合并后跟进 | … | … |
   **核对过什么**：（具体看了哪些文件、对照了哪些规则）
   **没核对什么**：（没跑测试、没连真机、没看哪些文件，原因）
   **修复与推送**：（无 / 修复提交 ID 与推送结果）
   ```

   存到 `docs/提测草稿-编码器<版本>/review/<仓库>-!<MR号>-第1轮.md`，不提交。
3. **贴进 MR**：把记录原文贴为 MR 评论，开头注明"评审由谁做、页面记录由谁贴"。贴完用接口读评论列表确认（见入口文件第 7 节第 3 条）。
4. **修复**：P0/P1 在对应仓库的同名分支上修，**一个问题一个提交**（`git commit -F <文件>`，中文，写"为什么改"），推送；子仓有新提交，**主仓指针另提一个提交**，并重新核对指针可达。修完在记录里追加下一轮，列出每条对应的修复提交 ID，再审。
5. **合并前复核（页面）**：MR 源提交 = 评审的提交；`detailed_merge_status = mergeable`；无冲突；确认"删除源分支"未勾选。
6. **点合并**，读接口确认 `state=merged` 和 `merge_commit_sha`，没有 squash。
7. **核对合并后状态**：该提交已在目标仓库 `develop`（`GET …/repository/commits/<sha>/refs?type=branch` 应含 `develop`）。

4.12.0 演练的结果（供参考）：`sub_common !37` 无问题；`sub_embedded !36` 发现并修复 1 个 P1（参数补丁只认嵌套的 `outputResolution.single/multi`，新版平铺的 `outputResolutionSingle/Multi` 被跳过，IAP 后恢复不了输出位数）；`factory-automation !2` 无 P0/P1、1 个 P2；主仓 `!134` 修复 1 个 P1（写配置/设零/Flash 状态和后台改参数/波特率没登记"设备忙"，交接时可能关串口中断写 Flash）和 1 个 P2。

### 2.4 CHANGELOG 条目归属核对（必做，主仓 MR 里）【已验证，4.12.0 里正是靠它发现了问题】

`CHANGELOG.md` 里已发布版本段（如 `## 4.11.0`）里的每一条，对应的提交必须真的包含在该版本的正式 tag 里。判断方法：

```bash
git merge-base --is-ancestor <条目对应的提交> encoder-plotter-vX.Y.Z && echo 在tag里 || echo 不在
```

不在 tag 里，说明它是该版本**之后**的改动，条目必须写在 `## [Unreleased]`，否则下一个版本的发版通知（取同名版本段）会漏掉它。**还要核对：**
- 已发布版本段的条目数应与 `develop` 一致：`git show origin/develop:CHANGELOG.md | awk '/^## 4\.11\.0/{f=1;next} /^## /{f=0} f' | grep -c '^\* '`；
- 同一个版本号只能有一个二级标题段（合并历史可能带回重复段和已删除的旧条目）。

✅ **完成标准**
- [ ] 每个子仓 MR 与主仓 MR 都有评审记录且已贴进 MR 页面，结论"可以合并"。
- [ ] 每个 MR 已合并（`merged`，非 squash），目标分支上能查到该提交。
- [ ] 主仓三个自有子仓指针都已被各自 `develop` 可达；`sub_algorithm` 的所在远端引用已登记。
- [ ] `origin/develop` 当前提交 = 主仓合并提交，`package.json` 版本与预期一致，CHANGELOG `[Unreleased]` 条目数符合预期。
- [ ] 工作区的未跟踪文件没被动过、没进任何提交。

**必须停下问人**：开始合并前确认范围与顺序；别人 MR 的处理（默认不管）。

## 3. 第 3 步 · 发布准备：`release/x.y.z`【已验证】

依据 `docs/branching.md`、`docs/build-and-release.md`。**这一步是代码和 git 操作，创建 tag 不在这一步。**

1. `git fetch`，确认本地 `develop` 与 `origin/develop` 一致且就是第 2 步合并后的提交。
2. `git switch -c release/x.y.z`（从最新 `develop` 开）。
3. 在该分支上：
   - `CHANGELOG.md`：把 `## [Unreleased]` 下**全部条目原文**移到新建的 `## x.y.z - YYYY-MM-DD` 段（插在 `[Unreleased]` 与上一个版本段之间）；`## [Unreleased]` 标题保留、留空；条目**不改字句**。
   - `package.json`：`version` 改成 `x.y.z`。`package-lock.json`：先确认仓库有没有，有就同步（4.12.0 时没有）。
   - 不改任何 gitlink。
4. **本地预演门禁**（预演，不是测试；**不要跑单元测试或构建，不要创建 tag**）：

   ```bash
   # 发布线 + gitlink 可达性（需完整历史、已 --init 的子模块；CI_COMMIT_TAG 只是变量，不创建 tag）
   CI_COMMIT_TAG=rc-vX.Y.Z-1 CI_COMMIT_SHA=$(git rev-parse HEAD) bash scripts/release-gate.sh check
   # 更新日志版本段（CHANGELOG_PARSER 指向 ci-templates 仓库里的 scripts/changelog.mjs）
   CHANGELOG_PARSER=<ci-templates 路径>/scripts/changelog.mjs node scripts/changelog-gate.mjs check
   ```

   版本门禁（tag 版本 = `package.json` 版本）静态核对即可。再自查 `sub_algorithm` 可达性（见第 2 步 2.1）。
5. **发布准备单独一个提交**（`git commit -F <文件>`，中文，例 `feat: 准备 4.12.0 发布，将四十项更新归入版本段`），推送 `release/x.y.z`。

✅ **完成标准**
- [ ] 远端 `release/x.y.z` 提交 = 本地，只比 `develop` 多这 1 个提交，只改 `CHANGELOG.md` 和 `package.json`。
- [ ] `[Unreleased]` 为 0 条；`## x.y.z` 段条目数 = 原 `[Unreleased]` 条数，逐条原文一致；上一个版本段条目数不变。
- [ ] 四个子模块指针与 `develop` 相同。
- [ ] 两项门禁预演退出码 0，输出已记录；`sub_algorithm` 可达性那一行已记录。

## 4. 第 4 步 · RC tag 与出包

### 4.1 建议 tag 名，**用户确认后才创建**【已验证】

先把"建议的 tag 名 + 依据 + 前置条件"告诉用户，写明"**未创建、待你确认**"：

- 格式 `rc-vX.Y.Z-N`，N 是 RC 轮次，从已有最大序号 +1（`git tag -l 'rc-vX.Y.Z-*'`；无则 `-1`）。已存在或作废的 tag **不重打**。
- 依据：tag 版本 = `package.json` 版本；CHANGELOG 有同名版本段；CI 触发规则 `^rc-v`；RC 必须在 `release/*` 或 `hotfix/*` 上（`release-line-gate`）。
- 前置：RC/正式 tag 是**受保护 tag，只有 Maintainer 能推**（推送被拒要原样报错，不绕过）。

### 4.2 创建并推送（只这一个 tag）

执行方（Claude+Codex 协作时是 Codex）：

```bash
git fetch
git rev-parse origin/release/x.y.z                 # 确认仍是第 3 步的提交
git cat-file -t rc-v4.10.0-1                       # 看历史 RC tag 类型（4.10.0-1 是轻量 tag，类型 commit），保持一致
git tag rc-vX.Y.Z-N                                # 在该提交上创建
git push origin rc-vX.Y.Z-N                        # 只推这一个，不用 --tags，不 force
git ls-remote origin refs/tags/rc-vX.Y.Z-N         # 核对指向 = 第 3 步的提交
```

注意：执行方按其规则会要求用户在**它的会话里**确认 tag 名；用户已在对话里确认过的，执行方可能仍要问一次，这是它遵守"tag 需用户在本会话确认"的规则，不是故障，不要催它绕过。

## 5. 第 5 步 · 整理提测文档（5 份，本地）【规范】

> 本节与第 6~8 步（飞书文档、自测、提测单）来自用户的《提测规范》，按它执行；我们这次演练只跑到"RC tag 推送"，**这几步没有亲手跑过**，首次执行时逐项核对并订正。

### 5.1 文档与标题

每个版本一组，标题统一 **`版本号-外部版-文件名称`**（有内部版提测时再出 `版本号-内部版-文件名称`）：

| 文件 | 标题示例 | 内容 |
| --- | --- | --- |
| 1 | `4.12.0-外部版-功能新增` | 本版新增功能清单 |
| 2 | `4.12.0-外部版-功能修改` | 本版功能修改，写清修改前、修改后 |
| 3 | `4.12.0-外部版-缺陷修复` | 缺陷现象、修复说明、影响范围 |
| 4 | `4.12.0-外部版-需求文档` | 每条需求的类型、文档、功能说明、测试方法、预期结果 |
| 5 | `4.12.0-外部版-自测报告` | 本次变更 + 外部版既有功能回归的自测结果 |

本地源文件放仓库 `docs/提测-X.Y.Z-rcN/`，文件名 `1-功能新增.md` 等；**导入飞书时文件名决定文档标题，导入前要按上表命名**。

### 5.2 通用规则

1. **必须有「是否外部版功能」列**，值为 `是` 或 `否（原因）`；外部版功能排在表格顶部，仅内部版/HTTP 工具的排后面。
2. 算法部门提测的条目在名称前加 **【算法】**，测试方法取自算法提测文档原文，不改写。
3. 条目 ID 全文统一：`N` 新增、`M` 修改、`B` 缺陷、`A` 仅算法文档内部使用；五份文档里同一条目 ID 必须一致。
4. 内容来源：`CHANGELOG.md` 当前版本段 + 对应提交说明 + 算法提测文档。**不凭印象写**，没有依据的描述标「待研发确认」。
5. 类型只有 新增 / 修改 / 删除；缺陷修复在需求文档里写「修改（缺陷）」。没有删除类需求时在表后写明「无删除类需求」。
6. 「文档」列：有 = 仓库内有对应文档（写路径）；无 = 无独立需求文档，以更新条目为准。
7. 文档密级一律 **L2**。

| 文档 | 列 |
| --- | --- |
| 功能新增 | ID、是否外部版功能、功能、功能描述、适用范围 |
| 功能修改 | ID、是否外部版功能、功能、修改前、修改后 |
| 缺陷修复 | ID、是否外部版功能、问题现象、修复说明、影响范围 |
| 需求文档 | ID、是否外部版功能、需求、类型、文档、功能说明、怎么测试、预期测试结果 |
| 自测报告 | 序号、是否外部版功能、类别（新增/修改/缺陷/回归）、自测项、型号、结果、备注 |

### 5.4 怎么判定「是否外部版功能」（查代码，不凭感觉）

| 看什么 | 结论 |
| --- | --- |
| 界面入口有 `v-if="isInternal"` | 仅内部版 |
| 「生产模式」开关（`version.html`，`isInternal` 才显示） | 生产模式及其内部功能仅内部版 |
| 修改参数、修改波特率（`parameter-modal`，需内部版 + 生产模式） | 仅内部版 |
| 「外圈局部」（`device.html` 里 `isInternal` 内） | 仅内部版；「内圈局部」「单圈标定」外部版可见 |
| HTTP 接口（`qa_api`，随 `EncoderHttpApi-*.zip` 交付） | 测开工具，不属于桌面外部版 |
| 外部测试包底部/设置显示（`version.js` 的 `testParts`） | 只对 `test-v*` 测试包生效；RC 包底部为 `vX.Y.Z-r` |

判不准的标「待确认」，不要默认写「是」。**开始前重新读一遍对应源码**，上表只是 4.12.0 时的结果，代码改了以代码为准。

3. 每条判定是否外部版功能；拿不准的记入「存疑项」交用户，不自己拍板。

### 导入 md 的做法（《提测规范》写的是"实测可行"）

0. **建任何东西之前，先看目录树里有没有已存在的同名父页面和文档**【已验证】（4.12.0 里 Codex 已经导入过五份，我没先看就又建了一个空白文档，造成多余的空白页）。已有的就核对内容，不要重建。核对方法（实测可用）：页面里 `document.querySelectorAll('table tr, [role=row]').length` 数表格行数，对照本地 md 行数（含表头）；**长文档是按需渲染的，先滚到底再数**；密级看页面上有没有 `L2`。
1. 在父页面行点 `+` → `上传及导入` → `导入在线文档` → `Markdown`，选文件。这样目标就是该父页面，**不会弹"导入到"选位置的对话框**。
2. 从页面右上角 `+` 导入会弹选位置对话框，且最近位置列表里不一定有目标，不推荐。
3. 要把已导入的文档挪到父页面：目录树里 `···` → `移动到`，在对话框里用"最近使用位置"的 chip 选目标，**不要点树里的行**（点不中），确认前看清目标高亮的是父页面。
4. 文档标题取自文件名，导入前先改好；已导入的可在目录树 `···` → `重命名`。
5. 改文档内容最省事的办法是删旧文档、重新导入（删除进回收站，30 天内可恢复）。

### 内置浏览器里导入不可用时的替代（舵机 0.26.0 演练里【已验证】）

「导入在线文档」需要弹出选文件窗口，**内置浏览器里它弹不出来**（这时改用能操作系统文件窗口的执行方式，如用户的 Chrome 或桌面控制）。替代做法是新建空白文档后粘贴表格：

1. 目录树里悬停父页面，行尾点 `+`（**不是**点节点名，那会折叠子节点；也**不要**点标题左边的图标位）→ 「文档」→ 「新建空白文档」。
2. 弹出"文档密级设置"，选 **L2**，确定。
3. 点标题输入文档名；点正文空白处，让光标落在正文。
4. 页面里执行脚本，把表格以 `text/html` 放进 `paste` 事件（`rows` 是二维数组）：

   ```js
   const esc = s => s.replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;');
   const html = '<table>' + rows.map(r => '<tr>' + r.map(c => '<td>' + esc(c) + '</td>').join('') + '</tr>').join('') + '</table>';
   const dt = new DataTransfer();
   dt.setData('text/html', html);
   dt.setData('text/plain', rows.map(r => r.join('\t')).join('\n'));
   document.activeElement.dispatchEvent(new ClipboardEvent('paste', {clipboardData: dt, bubbles: true, cancelable: true}));
   ```
5. 表格行很多时，在本机起带 CORS 头的小 HTTP 服务让页面 `fetch` 读本地 md 解析成 `rows`，**用完关掉**。
6. 这个方法只能粘贴**表格**；五份文档里如果还有表格以外的段落（例如"无删除类需求"一句），要另外手动输入或改用导入。**【未验证：含非表格内容的文档】**

## 8. 第 8 步 · 真机自测【规范】

### 8.1 原则

- **外部版功能优先**，再测仅内部版/HTTP 的。
- 自测必须有真实依据（连真机、跑脚本或人工操作）；没做的写「待测」。
- 会**写设备**的操作（再标定、设零、改参数、IAP）先确认设备、做好快照/备份，需要人工转动设备的和测试人员约定后再做。
- 测 RC 包时用 **external** 目录下的包，**不要用开发版代替**。
- **开始前用户必须明确授权，并确认设备型号、固件、读取器 SN、是否可以写设备**（入口文件第 3 节第 6 条）。

### 8.2 自测报告必须覆盖

1. 外部版：本次新增、修改、缺陷（每条一行）。
2. 外部版：既有功能回归：启动与版本显示、读取器连接/断开/重连与多读取器、编码器自动识别、实时读数、采集与导出、导入并绘图、普通再标定、速比与局部标定、设零、参数读取与配置、IAP 升级、日志导出。具体以外部版界面实际开放的为准。
3. 仅内部版 / 仅 HTTP 工具的条目（**单列**，不与外部版混在一起）。
4. 自动化测试（`build_info`、`safe_name`、`stator_check`、`sub_algorithm`、`sub_embedded`、`qa_api` 六组，CI gate 会跑）。

**结果列只能填 `待测` / `通过` / `不通过`；没做过的不填通过。**

### 8.4 已知结论（4.12.0 RC，来自《提测规范》，供下次对照）
