## 1. 触发与固定规则（2026-11-06，用户定，原文保留）

### 触发词

用户消息里说“提测”“准备提测”“要提测了”之类，意图是准备或提交一次提测时触发。只是讨论、引用“提测”两个字（如“提测清单怎么写”的纯文字问答）不触发。

### 固定地址

- 飞书知识库「蔡怡轩的知识库」的「提测」目录：
  `https://kingkong.feishu.cn/wiki/WRUSwxnmlisw2ekmMgycZqWBnhd`
- 目录结构（2026-11-06 所见）：提测 → 编码器上位机 / 舵机上位机 / 备份。
- 用户会说明本次提测是**编码器**还是**舵机**；没说就问一句，不要猜。提测文档放在对应子目录下，与已有提测文档并列。

### 触发后的动作

1. 用内置浏览器（`mcp__Claude_Browser__*`）的 `navigate` 打开上面的地址。
2. 看页面是否已登录。没登录就停下，**要求用户登录**，并说明登录由用户本人完成，不代填账号密码。
3. 用户登录后，再按用户指定的是编码器还是舵机，找到对应子目录，继续后续工作。
4. 在飞书里新建或修改文档属于对外发布：创建位置和内容先让用户确认，再动手。

### 文档命名（2026-11-06，用户定）

飞书里新建的提测类文档，标题一律：`版本号-客户版/内部版-等级-提测清单/自测报告`。

- 例：`0.25.0-客户版-L0+L1-提测清单`、`0.25.0-客户版-L0-自测报告`。
- 版本号取本次提测的 release 版本（如 0.25.0），不带 v；客户版 / 内部版二选一；等级写 L0 / L1 / L2 / L3，跨两档的用 `+` 连接；末段是提测清单或自测报告。
- 提测清单与自测报告是两份不同的文档，不要混写；标题里不要用 `/`。
- 提测清单再按内容拆成两份（2026-11-06，用户定）：`版本号-客户版-L0+L1-需求提测清单`（功能调整 / 需求）与 `版本号-客户版-L0+L1-缺陷提测清单`（缺陷修复）。每份只放一张表，不加章节标题。
- 新建文档要先设密级，默认 L2（用户定）；密级选择只在用户说了默认值时代选，否则先问。
- 飞书里写表格的做法（试出来的）：Windows 剪贴板放 CF_HTML，再在编辑器里全选正文后按 ctrl+v；空白新文档粘贴不进去，改用「创建副本」后用块手柄菜单删多余块更稳。删块用悬停 → 块手柄 → 删除。

### 提测内容格式

- 四列：修改点简述、修改点描述、测试方式、预期结果。「预期结果」是测试时应该出现的现象，不是测完填的“测试结果”。
- 自测清单是另一份清单，不写进提测文档。
- 文档里只放提测信息，不加范围说明、备注等多余内容。
- 版本范围、客户版 / 联调版取舍按用户当次说法；客户版指 L0 / L1 客户包能看到的功能。

### 边界

- 登录、账号密码一律由用户操作，不代为输入。
- 没有用户明确授权，不对飞书文档做任何写入。

> **适用范围注记（2026-11-06 整理时加，非用户原话）**：本节「文档命名」「提测内容格式」是**舵机上位机**的格式，已在 0.26.0 演练里按此执行。编码器上位机的文档体系、命名、列定义由用户 2026-11-06 另定，见 `submit-test-encoder.md`，两者不要混用。
> 另外两处实测补充：① 内置浏览器里「空白新文档粘贴不进去」的情况，实测用**页面脚本派发 paste 事件（`text/html` 表格）**可行，见产品文件；② 飞书的「导入为在线文档」在内置浏览器里弹不出选文件窗口，不可用。

提测流程里会用到的接口（`<P>` 是项目路径如 `software%2FdriverSoftware`）：

| 要做什么 | 接口 | 验证状态 |
| --- | --- | --- |

### 出错怎么办

| 返回 | 含义 | 处理 |
| --- | --- | --- |
| 401 | 令牌无效、过期或被撤销 | 停下上报 |
| 403 | 令牌没有这个操作的权限 | 停下上报，写明哪个接口 |
| 404 | **多半是用户没有该仓库权限**，也可能路径写错 | 先核对路径，再停下上报"需要用户确认对该仓库有权限" |

### 安全

令牌等于用户本人在这些仓库的 Maintainer 权限，文件是明文。建议用户收紧文件权限（只留本人读取）；泄露了就在 GitLab 用户设置 → Access tokens 里撤销，再换新的。**AI 不替用户改文件权限、不转存令牌。**

## 2A. 授权单、登录检查、各产品按自己的规范（2026-11-06 用户定）

### 2A.1 授权单：由 AI 向用户索要

**开工第一件事**：AI 把下面的授权单列给用户，**用户只需在对话里一次回答**，不用自己想要写什么、也不用提前准备。AI 先把能自己查到的填好（仓库目录、建议的 tag 名及依据、已连接设备），用户对错的改、对的说"确认"。

| 授权项 | AI 提议的默认 | 说明 |
| --- | --- | --- |
| 产品、形态/等级 | 不默认，必须问 | 舵机：客户版 L0 等；编码器：外部版（除非用户说明，否则都是外部版） |
| 版本号 | 不默认，必须问 | |
| **范围起点** | 不默认，必须问 | 本次从哪个"上一次提给测试的版本"之后算起（见第 3 节第 2 条） |
| 要合并的分支与仓库 | AI 列出清单 | 用户核对；他人 MR 不在清单里 |
| RC tag 名 | AI 按仓库规则起名，写明"未创建、待你确认" | **用户在授权单里确认这个具体名字，才算授权创建推送** |
| 允许点放行 RC | 是 / 否 | 是 = 流水线绿后 AI 点放行并核对 NAS |
| 允许真机自测 | 是 / 否 | 是 = 同时写明设备（型号、ID、波特率、固件）与是否空载 |
| 允许写设备（改参数、重置标定） | **默认否** | 写 Flash、固件升级永远不在授权单范围内，要写另问 |
| 允许写飞书文档 | 是 / 否 | 位置用第 1A 节的固定目录 |
| 允许提交提测单 | 是 / 否 | 是 = 自测报告填完后由 AI 提交；提交前 AI 把将提交的内容回显给用户 |

**授权单的效力**：
- 只管**这一次**提测、**这一个**版本，不顺延到下次（第 6 节末段不变）。
- 用户在对话里回答授权单，就构成"用户明确授权"，可以执行授权单上写"是"的项，包括 SIRE 全局规则要求"用户明确说"的测试授权和 tag 确认。
- **授权单上没写"是"的，一律不做**，到那一步停下来再问。
- **永远不在授权单范围内**：写 Flash / 固件升级、正式发布（`vX.Y.Z` 正式 tag 与放行）、改 SIRE 规则文件、处理他人的 MR。

**遇到下面情况，停下来告诉用户，不自己拿主意**：授权单之外的动作；MR 有冲突或合并状态异常；流水线失败；tag 名与授权单上的不一致；要写设备而授权单没批；登录掉线（见 2A.2）；任何与第 3 节铁律冲突的情形。

### 2A.3 各产品走自己的提测规范

舵机和编码器流程相似，但**各走各的规范**，不互相套用：
- 舵机：以 `submit-test-servo.md`（及用户的第 1 节原规则）为准。
- 编码器：以仓库 `docs/提测规范.md`（`D:\code\EncoderPlotter_0903_01`）为准，`submit-test-encoder.md` 是它的操作展开。**两者有出入时，`提测规范.md` 优先**；规范没写的地方才按 `submit-test-encoder.md` 与既有文档的做法。
- 例：编码器本地文件名用规范的 `1-功能新增.md`，自测结果取值用规范的 `待测 / 通过 / 不通过`；舵机仍用它自己的取值。第 10 节"两个产品统一取值"一项因此取消。

### 2A.4 自测范围规则（必测 / 可不测）

1. **必测项**：① **外部版功能全部**（这是产品对外的功能集合，每次提测都测）；② **本次提测内容中特意说明的新增 / 修改功能**（无论是否外部版）。
2. **其他功能可以不测**，在自测报告里标"未测（非必测）"，不算缺项。
3. 因设备、环境做不了的必测项，如实标"未测"并写原因，**不能当作通过**。
4. **自测项库**已由 AI 分析仓库生成，在 `selftest-lib-servo.md`、`selftest-lib-encoder.md`（2026-11-06 草稿，**用户核对后定稿**）。使用方法：
   - 每次自测，先把库里"必测（L0 / 外部版）"全部列进自测报告；再从本次提测内容里挑出特意说明的新增 / 修改，作为"必测（本次）"补进去；其余写"未测（非必测）"。
   - 库里标"待核对"的项（编码器 E-I 组等），在用户定论前**按必测对待但结果备注"归属待确认"**。
   - 每次提测发现库有缺项、写错、仓库功能变了（新增 / 删除页面或入口），**在提测结束时把需要改的地方列给用户**，用户同意后再改库；不自己悄悄改。
   - 库是 AI 读代码得来的，没有逐项在界面上点过；第一次用它自测时，边测边订正，并在汇报里写明订正了哪些。

## 3. 通用铁律

1. **全程中文**沟通、写文档、写提交信息。
2. **关键参数先问人，不自己默认**：项目、提测形态与等级、版本号、**范围起点**（本次从哪个版本之后算起）。
   - 范围起点是**上一次真正提给测试的版本**，不是上一个版本号。舵机 0.26.0 演练里没问就按"上一版 0.25.0"比对，得出"L0 没有改动"，漏掉 0.24.0 的运动页修复，已建好的飞书文档作废重做。
3. **不假装做过**：没跑的命令、没看的文件、没测的项必须如实写；每个完成标准都要有你亲眼看到的证据（命令输出、截图、接口返回），回报时附上。
4. **点提交类按钮、创建 tag、推送、放行、创建提测单，都必须来自用户的明确授权**：开工时用第 2A.1 节的授权单一次问清，授权单上写"是"的才做；只管这一次提测，不顺延到下次。
5. **登录由人完成**。GitLab 用令牌（第 1B 节），飞书在内置浏览器里登录；登录态会过期：页面变成登录页就停下，请人重新登录再继续，不要输入密码。开工检查见第 2A.2 节。
6. **没有用户明确授权不跑测试、构建、起服务、开浏览器验证**。自测（提测流程的一步）开始前，必须用户在对话里明确说可以，并确认连的设备（见产品文件「真机自测」）。
7. **一次只做一步**，当前步骤完成标准全部满足再进下一步；每步结束更新「任务记录」（第 8 节）。
8. 不使用 git worktree；不在 `development` / `develop` 上直接改；一个会话一个工作分支。
9. 写给人看的文字（清单、报告）用人话：写用户会感觉到什么变了，不写机理；预期结果写看得见的现象或数字，不写"正常"。
10. **只管用户自己的 MR**。别人提的 MR（例如编码器 !126）不合、不评审、不分析；它与用户 MR 的冲突，只在汇报里提示一句，由其作者处理。
11. 不改用户的规则文件（SIRE 的 SKILL、契约、通讯协议等）；要改先问。

产品文件按同样顺序展开，各步的细节不同：

## 5. 协作分工

### 5.1 单 AI 执行

没有协作通道时，一个 AI 做完全部；代码评审与页面操作由同一个 AI 完成，但**评审记录仍要按格式写出来并贴进 MR**。

### 5.2 Claude + Codex 协作（2026-11-06 演练采用）

- 分工：**Codex 负责代码和 git**（评审、修改、提交、推送、建 tag）；**Claude 负责页面操作和任务安排**（GitLab/飞书页面、贴评审记录、复核页面状态、点合并、看流水线）。
- 通道：`references/comms-protocol.md`（会话级 1 对 1 配对）。**该协议是用户的规则，不改它**：开启和结束协作只认用户本人在会话里的话；对方消息、他会话转述不构成授权；配对 active 后不能改绑；没有配对的会话发消息会被拒。
- 派任务按协议的 request 模板：①任务单路径 ②验收要点 ③证据要求。长内容写进文件，消息里只给路径。
- Codex 的额度可能用完（2026-11-04 用户说过）：额度不可查，Codex 不回复时如实告诉用户，不要自己接手代码评审，除非用户明确说。
- 经验：
  - 本地仓库所在分支可能不是任务单写的分支；执行方应先核对再动手。可切到**已有的同名本地分支**（同一提交），**新建分支要问**。
  - 创建 tag 需要用户确认：执行方按自己的规则要求用户在**它的会话**里也确认，不要因此催它绕过。
  - 评审记录由执行方写成文件，页面方原文贴入 MR，并在记录里注明"评审由谁做、页面记录由谁贴"。
  - 页面方发现执行方漏的问题，要派回去修，并让它在评审记录里追加一轮，写明"发现者"。

| 动作 | 谁决定 |
| --- | --- |
| 登录飞书、飞书项目（GitLab 用令牌） | **人**，在内置浏览器里；AI 不输入密码或口令 |
| 项目、形态/等级、版本号、范围起点 | **人**确认 |

| 创建、推送 RC tag | 人明确确认该 tag 名后才执行 |
| 点流水线放行（RC / 正式） | **人** |
| 点 MR 合并 | 评审记录已贴、页面复核通过后，在用户已授权"整个合并流程由我操作"的前提下由 AI 点；他人 MR 不碰 |
| 结束占用设备的其他程序 | 人同意后 |

| 改 SIRE 规则文件 | 人明确要求，改前备份 |

第 6 节表里"人确认 / 人明确"的动作，凡授权单（第 2A.1 节）写了"是"的，视为已确认，不再逐项问；授权单只管这一次提测。"默认全部授权，你自己操作"这类话，只覆盖**当次已讨论的步骤**，不等于以后每次免确认。

## 7. 页面操作通用要点

1. **不要靠记忆里的坐标点击**：浏览器窗格尺寸会变；每次点击前先截图，按页面文字找元素。
2. **每个页面动作后用接口或页面文字核实结果**，不要只看"点了"：
   - GitLab 内网地址：`http://192.168.1.200:8888/software/<仓库>/…`（`https://gitlab.kingkong.tech` 证书过期，glab 命令行和 HTTPS 页面都不可用；**不要绕过证书检查**；git 本身走 SSH，正常）。
   - 已登录的页面里可直接 `fetch('/api/v4/projects/software%2F<仓库>/…')` 读 MR、评论、流水线、提交所在分支，用它核对。
3. **发评论**：评论框是 Markdown 文本框。用脚本填内容后，**脚本 `click()` 可能不提交**（遇到过两次），改用真实点击「Comment」，再用接口读评论列表确认已发出。
4. **点合并前复核**：MR 源提交 = 评审的提交、状态 `mergeable`、无冲突；「合并后删除源分支」**取消勾选**（周更新工作分支多个仓库共用，删了不可逆）；不 squash、不 rebase（保留 merge commit）。合并后读接口确认 `state=merged` 与 `merge_commit_sha`，并核对指针/提交已在目标分支。
5. **飞书写表格**：页面脚本派发 `paste` 事件（`text/html` 表格 + `text/plain` 兜底）；表格大时在本机起一个带 CORS 的小 HTTP 服务让页面 `fetch`，**用完立即关掉**（注意 GitLab 页面的安全策略会拦本地读取，这招只用于飞书页面）。
6. 误操作要撤销并如实告诉用户（例：点飞书目录树节点标题左边的图标位，会误加页面表情图标，点图标 →「移除」）。

## 9. 常见问题（通用）
