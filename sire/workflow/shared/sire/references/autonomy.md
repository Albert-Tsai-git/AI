# 自主决策矩阵

**默认立场：自己决定，记录假设，继续推进。** 打断用户是例外，不是常态。

---

## 必须升级给用户的 5 类情形（只有这 5 类）

| # | 情形 | 例子 |
|---|---|---|
| 1 | 不可逆或破坏性操作 | 删数据库表、删文件、`git push --force`、清空目录、覆盖用户手写内容 |
| 2 | 外部副作用 | 发邮件/消息、发布上线、付费、调用生产环境、对外提交 PR |
| 3 | 凭据与密钥 | 需要账号密码、API key、token 才能继续 |
| 4 | 需求自相矛盾 | 两条要求互斥，且默认规则无法消解 |
| 5 | 范围爆炸 | 实际单元数超过分析预估 2 倍，或必须改动计划外的核心模块 |

**这 5 类优先于「不许卡点」铁律。** 命中时必须停下来，不得以「不阻塞全局」为由继续执行。

升级时给方案，不要开放式提问。默认值按可逆性分两种，**不许混用**：

可逆决策（第 4、5 类）—— 不回复就按推荐方案执行：
```
阻塞: [一句话]
建议: 方案A [做法]，理由 [一句话]
备选: 方案B [做法] / 方案C [做法]
默认: 你不回复我就按 A 执行
```

不可逆或有外部副作用（第 1、2、3 类）—— **不回复就不做**：
```
需要确认: [具体要做什么，影响哪些文件或数据]
影响范围: [能否撤销，撤销成本]
建议: 方案A [做法]
默认: 你不明确同意我就不执行，我先去做其他任务
```

对第 1、2、3 类写「不回复就执行」是严重错误，那等于把确认变成了通知。

## SIRE 任务列表确认门禁（用户明确指定，优先于默认自主决策）

在 R3 完成最小可执行 UNIT 列表、R4 复核通过后，R0 必须展示完整列表并等待用户确认。确认前不得进入执行阶段。只有用户明确说“不需确认”“自行完成”“直接执行”“按计划执行”等，才可跳过该确认，并记录原话和 `autonomous` 模式。该门禁不等同于风险升级，但同样是执行前置条件。

## 其余一律自主决策的默认规则

| 抉择 | 默认取法 |
|---|---|
| 技术选型 | 沿用项目现有技术栈，不引入新依赖 |
| 命名风格 | 沿用同目录既有命名，不另起一套 |
| 目录结构 | 放到同类文件所在目录 |
| 边界行为未定义 | 取保守且可回滚的一侧（宁可不做，不可做错） |
| 缺测试框架 | 写最小可运行验证脚本，放 `.sire/runs/<RUN_ID>/evidence/` |
| 错误处理未指定 | 捕获 + 记日志 + 不吞异常 |
| 需求描述含糊 | 取字面最小实现，把扩大解释写进假设清单 |
| 性能未指定 | 先正确后性能，性能项记为技术债务 |
| 注释语言 | 中文 |

## 假设记录格式

每条假设写入 `.sire/runs/<RUN_ID>/assumptions.md`：
```
A-01 [假设内容] | 影响: [如果假设错了会怎样] | 推翻成本: 低/中/高
```

最终报告里集中呈现，供用户一次性确认。**不要为了确认假设而中断执行。**

---

## 反模式（明令禁止）

- 问「你想怎么做」而不给方案
- 一个模糊点就停下来等回复
- 把能查证的事情拿去问用户（先查代码、查知识库、查文档）
- 为了显得谨慎而反复确认同一件事
