# 舵机上位机提测 · 逐步执行手册（SIRE 提测工作流产品文件之一）

> 本文是 `submit-test.md`（入口与通用规则）的配套文件。**用户 2026-11-06 定制的触发、命名、格式规则以 `submit-test.md` 第 1 节为准**，本文与之冲突时以第 1 节为准。通用铁律、授权边界、协作分工、页面操作要点见入口文件第 3、5、6、7 节，本文只写舵机特有的步骤。

> ## ⚠ 适用范围：**只用于「舵机上位机」**（仓库 `driverSoftware`）
> 编码器上位机（仓库 `EncoderPlotter`）的发布方式、tag 命名、分支名、包名、NAS 目录、提测模板都不同，**不要套用本文**，请看 `submit-test-encoder.md`。
> 本文的命令、tag（`rc-vX.Y.Z-N`）、分支（`development`）、档位（L0~L3）、飞书目录（提测 → 舵机上位机）、飞书项目空间「舵机项目」、提测单草稿（「上位机提测」）都是舵机专用的。

> **这份文档是给任何 AI 执行的操作手册**（Claude、Codex 或其他），不依赖某个工具的特有功能。
> 每一步写明：做什么、怎么做、做到什么程度算完成、出问题怎么办、什么时候必须停下来问人。
> 版本：2026-11-06 第一版，依据 0.26.0 客户版 L0 的完整提测演练整理。所有命令和操作都在那次演练里实际跑过；没跑过的会标「未验证」。

## A. 执行者须知（先读完再开始）

### A.1 你需要具备的能力

| 能力 | 用来做什么 | 没有怎么办 |
| --- | --- | --- |
| 在仓库里运行 shell、git | 第 2、3 步 | 停，告诉人缺什么 |
| 控制一个浏览器（打开页面、点击、输入、截图、执行页面脚本） | 第 5、8、9 步，查流水线 | 停 |
| 控制桌面（截图、点击、输入），并能看到真实屏幕 | 第 7 步真机自测 | 第 7 步停，不要用脚本代替 |
| 读写本机文件 | 全程 | 停 |

### A.2 铁律

1. **全程中文**沟通、写文档、写提交信息。
2. **不假装做过**：没跑的命令、没看的文件、没测的项，必须如实写出来。每个「完成标准」都要有你亲眼看到的证据（命令输出、截图、页面文字），回报时附上。
3. **关键参数先问人，不自己默认**（见 B 步骤）。尤其是**提测范围起点**。
4. **点提交类按钮前问人**：创建 tag、推送、放行、创建提测单，每次都要人明确说"可以"。
5. **登录由人完成**。需要登录就打开页面，请人登录，等人说"好了"再继续。不要自己输入密码、口令、令牌。
6. **一次只做一步**，当前步骤的完成标准全部满足，才进入下一步。
7. **每次开始前和每步结束后，更新「提测任务记录」**（A.4），这样上下文被压缩或换了 AI，也能接着做。
8. 不使用 git worktree，不在 `development` 上直接改，一个会话一个分支。
9. 写给人看的文字（清单、报告）用人话：写用户会感觉到什么变了，不写机理，删掉"综上所述"这类话。

### A.3 什么叫"做到什么程度"

每一步末尾有「✅ 完成标准」清单，**全部勾上才算完成**。拿不准的项，不要当通过，写成「待确认」交给人。

### A.4 提测任务记录（必须维护）

在 `docs/提测草稿-舵机<版本>-<形态>/任务记录.md` 里维护，不提交。开始时按下面模板创建，每步后更新：

## C. 第 2 步 · 走发布流程到 RC 包

**目的**：产出一个已通过门禁、Windows 和 macOS 都打好的 RC 包。依据：`docs/release-branching.md`。
**注意**：提测用 **RC 包**。不是正式包（`vX.Y.Z`），也不是测试包（`make_release.py test`，那是另一条线，不走本手册）。

### C.1 确定版本号

1. 打开 `CHANGELOG.md`，看 `## [未发布]` 的「新增」「修复」。
2. 逐条对账：`git log <上次发版tag>..HEAD --oneline`，别人漏写的条目补写到 CHANGELOG。
3. 判定：有「新增」升 minor，只有「修复」升 patch。实际口径是新增 ≥2 条升 minor，1 条升 patch。
4. 把建议版本和依据发给人，人确认。（这是第 1 步第 3 个参数。）

### C.2 前置检查

```bash
git fetch --all --prune
git status                    # 必须干净
git branch --show-current     # 记录当前分支
git tag -l "rc-v*" | tail     # 看已有的 RC 序号
```

要提测的改动必须已经合进 `development`（走过 MR、review、合并）。如果还有没合的，**停**，告诉人。

### C.3 创建 release 分支并 bump

```bash
git switch development && git pull
git switch -c release/X.Y.Z
```

Windows 上运行（**必须带 `PYTHONUTF8=1`**，否则遇到中文文件名因 gbk 解码报错，这是脚本缺陷，尚未修）：

```bash
PYTHONUTF8=1 python scripts/release.py X.Y.Z
```

PowerShell 写法：`$env:PYTHONUTF8=1; python scripts/release.py X.Y.Z`

脚本会：校验 CHANGELOG、更新 `VERSION` 和 `electron/package.json`、截断 CHANGELOG、提交"发布准备"。**不会**打 tag。

✅ **完成标准**
- [ ] `git log -1` 是 `release: 准备 vX.Y.Z 发布`。
- [ ] `cat VERSION` 输出 `X.Y.Z`。
- [ ] `CHANGELOG.md` 里有 `## [X.Y.Z]` 段，`## [未发布]` 段下只剩空的 `### 新增`、`### 修复` 标题。

### C.4 本地先跑门禁（确认流程没问题再推）

```bash
python scripts/release_gate.py selftest
python scripts/release.py X.Y.Z --check-changelog
python -m pytest tests/unit -q -rs
```

> `release_gate.py check` 需要 CI 环境变量（`CI_COMMIT_TAG`、`CI_COMMIT_SHA`），本地跑不了，由流水线执行。

✅ **完成标准**：三条命令都退出码 0；pytest 记下通过数。任何一条失败，**停**，把输出给人，不要绕过。

### C.5 创建并推送 RC tag（人确认后）

1. tag 名：`rc-vX.Y.Z-N`，N 从 1 起，取已有最大序号 +1。**已经用过、作废的序号不能复用。**
2. 把"建议的 tag 名 + 依据 + 当前提交"发给人，写明「未创建，待你确认」。
3. 人说可以之后：

```bash
git tag rc-vX.Y.Z-N
git push origin release/X.Y.Z
git push origin rc-vX.Y.Z-N
```

### C.6 看流水线

**怎么查**：浏览器里登录内网 GitLab（`http://192.168.1.200:8888`，由人登录），打开项目 `software/driverSoftware` 的流水线。也可以在已登录的页面里执行：

```js
await fetch('/api/v4/projects/software%2FdriverSoftware/pipelines/<流水线ID>/jobs?per_page=50')
  .then(r => r.json()).then(j => j.map(x => x.name + ':' + x.status).join(', '))
```

> `https://gitlab.kingkong.tech` 的证书已过期，glab 命令行和 HTTPS 页面都不可用；**不要绕过证书检查**，走上面的内网地址。git 本身走 SSH，正常。

**必须出现这些任务**：`release-line-gate`、`version-gate`、`changelog-gate`、`test-gates`、**`build-win-rc`、`build-mac-rc`**，以及 `notify-rc-staged`、`release-rc`。

> ⚠ 0.26.0 演练里 RC 流水线曾缺 `build-mac-rc`，只出 Windows 包。看到只有 `build-win-rc` 就停下告诉人：`.gitlab-ci.yml` 要补，补完要**重打新的 RC tag**（旧 tag 不能复用）。

**已知偶发**：`test-gates` 里 `test_spawn_ring_never_replays_or_tears_samples` 在 macOS 上偶尔超时，重跑一次；连续失败才算真问题。

**runner**：Windows 用 runner #11（标签 `win`），macOS 用 `macos-arm64-cyx`。任务长时间 pending，先查 runner 是否在线，报告给人。

✅ **完成标准**
- [ ] 四个门禁任务都是 `success`。
- [ ] `build-win-rc`、`build-mac-rc` 都是 `success`。
- [ ] `release-rc` 状态是 `manual`（等人点）。

### C.7 放行（人点）

**请人**在流水线里手动点 **`release-rc`**。（`docs/release-branching.md` 写的是 `release-nas`，实际流水线里 RC 的放行任务叫 `release-rc`，以流水线为准。）

人说"已放行"之后，你自己验证：

```powershell

Test-Path '\\KingKongNAS\software\02SD\staging\rc-vX.Y.Z-N'     # 应为 False
```

✅ **完成标准**
- [ ] `rc\vX.Y.Z-N\` 下有 Windows 的包（`SensorDriveWebGUI Setup X.Y.Z.exe`、`…-win.zip`、`customer-L0`、`customer-L1` 各一套）。
- [ ] `rc\vX.Y.Z-N\mac\` 下有对应的 `.dmg` 和 `.zip`。
- [ ] `staging\rc-vX.Y.Z-N` 已不存在。

**必须停下问人**：创建 tag 前；点 `release-rc` 放行。

## D. 第 3 步 · 按等级检索仓库，整理需求和缺陷

**目的**：得到这次提测等级下**用户看得到**的需求清单和缺陷清单。**每次都重新查，不沿用上次的清单。**

### D.1 档位对照（以代码为准）

依据 `frontend/js/capabilities.js` 的 `CAP_MIN_LEVEL`。**开始前重新读一遍这个文件**，下表只是 0.26.0 时的结果，代码改了就以代码为准。

| 档位 | 能看到 |
| --- | --- |
| L0 客户 | 运动页、设备页、使用指南 |
| L1 | L0 + 轨迹页、运动页「附加寄存器」、多设备相关（多设备采集、总线设备列表、快速换台、识别测试报告等） |
| L2 | L1 + 标定、下线检测、力感知标定、扭矩标定 |
| L3 | L2 + 寄存器、控制台、测试套件（含电机检测）、诊断 |

### D.2 检索步骤

1. 列出范围内的版本：`CHANGELOG.md` 里从「范围起点」之后到本次版本的每个 `## [x.y.z]` 段（不含起点本身）。
2. 逐条读每段的「新增」「修复」，对每一条回答一个问题：**在本次提测等级下，用户看得到吗？**
   - 看得到 → 进清单。
   - 看不到（属于更高档位的页面）→ 不进清单，记在「划分依据」里。
   - 拿不准 → 记入「存疑项」，**交给人**，不自己拍板。
3. **只看 CHANGELOG 不够**，再查代码改动：

   ```bash
   git diff --stat <范围起点tag> release/X.Y.Z -- frontend core server.py
   ```

   找 CHANGELOG 没写、但影响该等级可见页面的改动。注意：只改了注释的改动不算功能改动，但要看一眼确认。
4. 把已有的历史清单当底稿可以（如 `docs/提测清单-客户版-0.20.4至0.25.0.md`），但**每一条仍要对照 CHANGELOG 和代码重新确认**，别整份照抄。
5. 单独加一条「版本号更新」（顶栏版本变成 vX.Y.Z），放需求清单第一行。

### D.3 每条清单怎么写

四列：`修改点简述 | 修改点描述 | 测试方式 | 预期结果`。

| 列 | 怎么写 | 反例 |
| --- | --- | --- |
| 修改点简述 | 4~12 个字，能当目录 | "优化" |
| 修改点描述 | 一两句人话：用户会感觉到什么变了 | "重构了 ring buffer 的 cursor 逻辑" |
| 测试方式 | 具体操作，能照着做 | "测一下" |
| 预期结果 | 看得见的现象或数字 | "正常" |

本次范围内确实没有的，写一行「无」，不留空表。

### F.4 创建文档的操作（内置浏览器，逐项验证过）

> 飞书的「导入为在线文档」在内置浏览器里**用不了**（点了弹不出选文件窗口），不要试。用下面这套。
> **不要靠记忆里的坐标点击。浏览器窗格宽度会变，每次点之前先截图，按页面上的文字找元素。**

1. 鼠标移到左侧目录树里「舵机上位机」那一行，行尾出现 `+` 和 `···`。点 `+`（**不是**点节点名，点节点名会把子节点折叠起来；也**不要**点标题左边的图标位，会误加表情图标）。
2. 菜单第一项「文档」，点它。
3. 弹出模板窗口，点最前面的「新建空白文档」。
4. 弹出「文档密级设置」，选 **L2**，点「确定」。不设密级无法编辑。
5. 点标题输入框，输入文档名。
6. 点正文空白处，让光标落在正文。
7. 在页面里执行脚本，把表格以 `text/html` 放进粘贴事件（下面是 `rows` 为二维数组时的写法）：

   ```js
   const esc = s => s.replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;');
   const html = '<table>' + rows.map(r => '<tr>' + r.map(c => '<td>' + esc(c) + '</td>').join('') + '</tr>').join('') + '</table>';
   const dt = new DataTransfer();
   dt.setData('text/html', html);
   dt.setData('text/plain', rows.map(r => r.join('\t')).join('\n'));
   document.activeElement.dispatchEvent(new ClipboardEvent('paste', {clipboardData: dt, bubbles: true, cancelable: true}));
   ```

9. 等 3~5 秒，截图确认表格出现。

**要替换旧文档内容时**：点表格下方空白处，`Ctrl+A` 两次（第一次选表格，第二次选全文），`Delete`，再重新粘贴。

## H. 第 7 步 · 用真实安装包真机自测

**目的**：在真机上，像真实用户那样操作 RC 安装包，把每一项的实际结果记下来。

### H.1 前提（逐项确认）

1. **问人**：连的是哪台设备、是不是空载、手是否离开输出轴。**人没确认设备，不要使能电机。** 没有设备就把真机项都标「未测」并写原因，不要假装测过。
2. **用真实安装包**，不用源码、开发服务：
   - 客户版 L0：`SensorDriveWebGUI-customer-L0 Setup X.Y.Z.exe`；客户版 L1：`…customer-L1 Setup…`；内部版：`SensorDriveWebGUI Setup X.Y.Z.exe`。
   - 从 NAS `rc\vX.Y.Z-N\` 拷到本机临时目录。
3. 安装到**独立目录**，不覆盖机器上已有版本。安装向导里把安装目录改成例如 `D:\file\sensor\SensorDriveWebGUI-customer-L0`（先看一眼向导默认目录是不是人正在用的版本）。装完把"安装后立即运行"取消，由你自己控制启动。
4. **占用检查**：一个分析仪同一时间只能被一个程序占用。启动前查本机有没有别的程序占着设备：

   ```powershell
   Get-NetTCPConnection -State Listen -LocalPort 8765 -ErrorAction SilentlyContinue
   ```

   端口被别的开发服务占着时，**先问人**，同意后才结束那个进程。注意别的会话可能随后又把它拉起来，测试中发现设备被抢要重新排查。
5. 窗口必须出现在**人能看到的真实桌面**上，保持可见，别最小化、别藏在别的窗口后面。人要能全程看着。

> **自测范围与项库（2026-11-06 用户定）**：外部版 = 客户版 L0。自测项以 `selftest-lib-servo.md` 为准：L0 项全部必测，加上本次提测内容里特意说明的新增 / 修改；L1 及以上其余可不测。授权与停手规则见 `submit-test.md` 第 2A 节。

### H.2 怎么测

- **在界面上点**，像真实用户。不要用脚本调接口代替点击。
- 个别无法在界面上完成的检查（例如客户包的台架接口应返回 403）可以单独用接口核对，但报告里要写明"用接口核对"。
- 客户包的后端端口是随机的，先找：

  ```powershell
  $ids=(Get-CimInstance Win32_Process | Where-Object { $_.Name -like 'SensorDrive*' }).ProcessId
  Get-NetTCPConnection -State Listen | Where-Object { $ids -contains $_.OwningProcess } | Select-Object LocalPort
  ```

  核对 `GET http://127.0.0.1:<端口>/api/meta`：`app_version` 应为本次版本，`internal` 为 false，L0 的 `maxLevel` 为 0。
- 使能电机时只下发**小幅**指令：位置约 0.05 rad、KP 取小值；力矩约 0.05 N·m、KP=0。**每轮测完点「失能」**，并确认状态回到 kStopped、故障位没亮。
- 参考顺序（可按实际调整）：连接 → 运动页采集（各档采样率）→ 使能与指令 → 导出导入 → 设备页 → 软复位 → 重启应用 → 使用指南 → 接口核对。

### H.3 自测报告怎么建

以本次提测的需求、缺陷清单为准，每一条至少对应一个测试项；再加一批「基础回归」项，确认客户能用的基本功能没被影响。七列见 F.2。

- 「分类」：基础回归 / 需求 / 缺陷。
- 「测试步骤」「预期结果」可以参考清单里的「测试方式」「预期结果」，但要具体到能直接照着做。
- 需要**特殊条件**的项（两台舵机、无固件设备、7.5 Mbaud、Mac）在预期结果末尾写明条件，没条件时记「未测」。

### H.4 回填规则

**「实际结果」**：写看到的现象和数字，不写"正常""没问题"。例：「实测 100.1 Hz，可正常结束」。

**「结论」只用这几个词**：

| 词 | 用在什么时候 |
| --- | --- |
| 通过 | 预期结果全部满足 |
| 通过（原因） | 满足，但次数或范围不足，括号里写清，例如「通过（次数不足 20）」 |
| 部分通过 | 一部分验证了，另一部分没验证，实际结果里写清各是哪部分 |
| 待确认 | 与预期有偏差，但你不确定算不算问题。**写出数字，不要自己判通过或不通过** |
| 未测 | 没做，实际结果里写原因（没有 Mac、只接了一台等） |
| 未对比 / 未核对 | 需要和别的东西对比或解密才能判断，而这次没做 |

**不允许**：没测却写通过；预期与实际不符却写通过；没测的项不写原因。

### H.5 固件升级

涉及写 Flash，**本流程默认不测**。设备页的固件升级区块只核对"区块在不在"。人明确要求才测，并且写 Flash 前再问一次。

### H.6 测试中产生的文件

CSV、JSON、诊断包会落在 `Downloads`。诊断包是加密的，不要尝试破解；人要核对内容时由人录入口令解密。在最后的回报里列出这些文件的位置。

✅ **完成标准**
- [ ] 自测报告每一行的「实际结果」「结论」都已填写，没有空格。
- [ ] 每个「未测」「部分通过」「待确认」都有原因或数字。
- [ ] 测试结束时电机已失能，状态 kStopped。
- [ ] 本地自测报告 md 已保存。
- [ ] 回报里给出：各结论的数量、所有「待确认」项、所有「未测」项及原因。

**必须停下问人**：设备确认前；占用设备的程序要结束前；任何要写 Flash 的操作前。

## M. 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| `release.py` 报 `UnicodeDecodeError` | 中文文件名 + gbk。加 `PYTHONUTF8=1` |
| 流水线只有 Windows 构建 | CI 缺 `build-mac-rc`。补上后重打新 RC tag，旧 tag 不能复用 |
| `test-gates` 偶发失败 | 已知的共享采样环用例在 macOS 偶尔超时。重跑一次，连续失败才算真问题 |
| glab 或 GitLab HTTPS 打不开 | 证书过期。git 走 SSH，网页走内网地址，不绕过证书检查 |
| 飞书导入文档弹不出窗口 | 用 F.4 的粘贴法 |
| 粘贴表格没反应 | 光标没在正文，重新点正文再粘贴 |
| 误给页面加了表情图标 | 点图标 → 点「移除」 |
| 目录树里节点被折叠了 | 刚才点到了节点名，重新展开，找 `+` |
| 点击老是落空 | 窗格尺寸变了，截图后重新定位，不用旧坐标 |
| 提测清单写成"L0 没有改动" | 先怀疑范围起点取错，回第 1 步 |
| 本机端口被别的开发服务占着 | 先问人，同意后再关；之后可能被重新拉起 |
| 窗口出现在另一个显示器上 | 截图时切换到对应显示器，或请人把窗口拖过来 |
| 指南窗口里切语言，主界面也变了 | 两者共用语言设置，不是缺陷 |
| 1 kHz 采集实测只有约 850 Hz（1 Mbaud） | 目前记「待确认」，尚未判定是否正常 |
| 使能时选 1 Hz，实际按 5 Hz 采 | 设计如此（固件看门狗要求），日志里有说明 |
