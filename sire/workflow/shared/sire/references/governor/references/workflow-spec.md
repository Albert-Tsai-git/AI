# AI Workflow Governor：实施规范

## 1. 目标与适用范围

本规范把一次 AI 请求管理成一个“可验证交付项目”，目标是：

1. 由 AI 自动承担检索、分析、拆分、调度、执行、复核、测试和知识沉淀，尽量减少人工协调。
2. 通过角色分离、可追溯证据和质量门禁提高交付质量。
3. 允许并行推进独立任务，同时让每个任务保持完整闭环。
4. 只在权限、业务取舍、主观验收或不可验证的高风险问题上请求人工决策。

适用于多步骤的软件变更、文档/表格/演示文稿交付、研究分析、数据处理、方案设计、配置变更和其他需要验收的工作。单一事实问答、简单改名或一处无风险格式修改可走轻量路径，但只要存在多个目标、依赖、外部副作用或验收要求，就必须走本规范。

## 2. 核心控制原则

### 2.1 “完成”的定义

完成不是“生成了结果”，而是同时满足：

`需求覆盖 + 执行产物存在 + 独立复核通过 + 功能/可用性测试通过 + 集成验收通过 + 知识已沉淀`

任意一项缺失，状态只能是 `INCOMPLETE`、`BLOCKED` 或 `NEEDS_INPUT`。

### 2.2 角色分离

角色是责任边界，不要求一定启动多个模型。可由同一模型在不同上下文/阶段模拟，但必须明确标注角色并重新审视结果。执行者不能作为唯一复核者；如果资源允许，优先把需求复核、执行和测试分配给不同 worker。

### 2.3 最小人工介入

AI 默认自行完成可推断的技术决策。人工只接收结构化决策包，不被要求重新阅读全部过程。决策包仅针对无法安全推断的一个或几个问题，并包含推荐选项和影响。

### 2.4 证据优先

每一个状态跃迁都需要证据。命令成功不等于功能正确；评审意见不等于测试通过；测试通过也不等于需求完整。三类证据需要分别记录。

### 2.5 轻量路径与稀疏输入

单一步骤、可逆、低风险且无实质歧义的请求走轻量路径：直接处理并做语义/语法自检，不强行创建完整账本。短描述本身不代表可以猜测关键事实。对于受治理任务，只能推断低影响、可逆的默认值并显式列出；凡缺失信息会影响测试、范围、目标选择、权限或高影响结论，必须形成 blocker/decision packet，只索取确切缺口。不得虚构文件、数据、凭据、目标或验收标准。

## 3. 角色职责与交付物

| 角色 | 必须回答的问题 | 交付物 | 是否可批准自己的产物 |
|---|---|---|---|
| Orchestrator 流程编排者 | 做什么、先做什么、哪些可并行、哪里被阻塞？ | 范围声明、依赖图、队列、状态汇总 | 否，最终关闭需 Closure Auditor |
| Knowledge Curator/Indexer 知识管理员 | 是否做过？能否复用？新知识如何被找到？ | KB-Check、知识条目、索引 | 否，条目需可追溯到验证证据 |
| Requirement Analyst 需求分析者 | 用户真正要的结果和验收标准是什么？ | REQ 清单、约束、非目标、风险 | 否，需求需经 Requirement Reviewer |
| Task Decomposer 需求拆分者 | 如何变成独立、可执行、可验证的小单元？ | UNIT 卡、依赖 DAG、执行顺序 | 否，拆分需经 Requirement Reviewer |
| Requirement Reviewer 需求复核者 | 是否漏项、歧义、过大、不可测或顺序错误？ | 拆分复核结论、缺陷清单 | 是，复核结论本身需有理由 |
| Executor 执行者 | 如何在范围内产出结果？ | 代码、文档、数据、配置或分析结果 | 否 |
| Work Reviewer 工作复核者 | 产物是否满足 UNIT 和约束，是否引入回归？ | 复核报告、通过/失败、修复建议 | 否，不能替代测试 |
| Functional Tester 功能测试者 | 结果是否在真实使用路径上工作？ | 测试记录、输入、期望/实际、证据 | 否 |
| Integrator 集成者 | 单元组合后是否仍满足整体需求？ | 集成测试、回归结论、发布前清单 | 否 |
| Closure Auditor 闭环审计者 | 是否每条需求、每个单元和每道门都有证据？ | 关闭结论、未决项、交付摘要 | 是，负责最终审计 |

## 4. 状态机与门禁

```text
INTAKE
  → KB_CHECKED
  → ANALYZED
  → DECOMPOSED
  → DECOMPOSITION_REVIEWED
  → READY
  → EXECUTING
  → REVIEWED
  → TESTED
  → DONE

REVIEWED/TESTED 失败 → EXECUTING（带 remediation_id）
任何阶段遇到外部/人工依赖 → BLOCKED（继续其他可行分支）
```

### 门禁 A：知识门

- 必须列出搜索范围、关键词/路径和命中结果。
- 必须明确“复用、改造、避免、无匹配”之一。
- 发现已有实现时，先验证其适用性和测试状态，再决定是否重做。

### 门禁 B：需求门

- 每条 REQ 都有可观察的验收标准。
- 约束、非目标、风险和输入输出清楚。
- 不能从上下文推断的高影响决策进入决策包。

### 门禁 C：拆分门

- 每个 UNIT 只有一个主要可验收结果。
- UNIT 可在有限上下文内执行，有明确产物和测试。
- 依赖、并行安全性、共享资源冲突和失败恢复已记录。
- 存在 `REQ → UNIT` 覆盖关系，不能有孤儿需求。

### 门禁 D：单元质量门

- 执行后立即复核和测试。
- 复核与测试必须分别给出 verdict 和证据。
- 失败必须产生缺陷与 remediation，不得用文字解释替代修复。
- 三次相同失败后换策略并形成 blocker；仍可推进其他 lane。

### 门禁 E：集成关闭门

- 所有 UNIT 为 DONE 或有明确人工决策的 BLOCKED。
- 所有 REQ 有证据映射。
- 集成/端到端测试通过。
- 知识条目和索引已更新。

允许某个安全产物已 `DONE` 而另一条 lane 为 `BLOCKED`；但只要仍有必需需求无法满足，总体任务必须保持 `BLOCKED` 或 `NEEDS_INPUT`，不能把部分完成报告为整体完成。

## 5. 并行调度算法

1. 将 UNIT 表示为有向无环图：边 `A → B` 表示 B 依赖 A。
2. 将无未完成依赖的单元放入 `READY` 队列。
3. 对每个 READY 单元检查共享文件、数据库、外部系统和权限；有冲突则串行化。
4. 为每个 lane 分配 Executor、Reviewer、Tester 或其明确的模拟角色。
5. 任一 lane 完成闭环后，解除其后继依赖；失败只影响依赖它的 lane。
6. 被阻塞的 lane 必须记录阻塞原因、解除条件、下一次动作和可继续的旁路工作。
7. 当所有剩余工作都依赖同一个 blocker，才暂停主流程并请求人工输入。

## 6. 复核与测试标准

复核至少检查：

- 对应 UNIT 和 REQ 是否完整实现；
- 约束、格式、项目约定和安全边界；
- 失败路径、边界条件和回归风险；
- 产物是否可被下游任务实际消费。

测试按风险选择最小充分集合：

- 软件：单元/静态检查 → 目标功能测试 → 回归/集成测试；
- 游戏：规则/状态转移 → 输入边界 → 胜负与异常路径；
- 音乐：拍数/时值/音符事件结构 → 渲染或播放检查 → 听感复核；
- 解析：合法输入 → 缺失/非法输入 → 边界结构与错误信息；
- 文学：主题/意象/篇幅/结构约束 → 一致性检查 → 文风与意义复核；
- 创意：输出 schema/约束 → 内部一致性 → 新颖性与适配度复核；
- 文档/演示：结构检查 → 渲染或页面检查 → 关键内容抽样；
- 表格/数据：模式/公式检查 → 样例计算 → 汇总和边界校验；
- 研究/分析：来源核验 → 方法/计算重现 → 结论与需求对照；
- 配置/运营：差异检查 → 模拟/沙盒验证 → 实际验收（需授权）。

结构、数值、格式和状态可以自动验证；音乐听感、文学感染力、创意新颖性等主观质量必须保留独立 Work Reviewer 或人工验收，不能被自动化断言替代。

## 7. 知识库与索引规范

如果项目已有知识库，遵循项目约定。没有时，建议在工作区建立：

```text
knowledge-base/
├─ index.md
├─ decisions/
├─ solutions/
├─ failures/
└─ templates/
```

每个条目必须包含：标题、类型、适用场景、问题、决策/方案、关键约束、验证证据、局限、标签、创建/更新时间和关联 artifact。索引至少按主题、关键词、技术/业务域和关联任务链接组织。

知识管理员不应把过程日志全部倒入知识库，只提炼未来任务能复用的判断、方案、测试方式、失败模式和限制。禁止记录凭据、隐私数据和无必要的原始敏感内容。

## 8. 质量与效率指标

建议持续记录以下指标来改进流程：

- 首次通过率：单元首次复核和测试同时通过的比例；
- 返工率：发生 remediation 的单元比例；
- 需求覆盖率：有通过证据的 REQ / REQ 总数；
- 自动闭环率：无需人工决策即可 DONE 的任务比例；
- 并行效率：关键路径耗时 / 实际墙钟耗时；
- 知识复用率：使用既有 KB 条目的任务比例；
- 阻塞恢复时间和相同失败重复次数。

指标用于发现流程问题，不得替代验收，也不能为了提高数字而省略测试。
