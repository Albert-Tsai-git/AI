## 执行阶段

### 阶段1: 需求分析
- **角色1**: 读取进化知识库 → 分析需求 → 拆解 → 生成需求列表 → 时间预估
- **角色2**: 交叉对比 → 查漏补缺 → 生成最终需求清单
- **角色6**: 编写测试用例（角色2校验后）
- **角色5**: 审查测试用例质量
- **角色7**: 阶段1评估
- **角色8**: 创建过程文档（初始） → 收集需求内容

### 阶段1.5: 架构设计
- **角色3+角色4**: 协作制定技术方案
- **角色5**: 预审架构方案
- **角色7**: 阶段1.5评估

### 阶段2: 并行开发与审查闭环
- **角色3/角色4**: 并行开发 → 增量review → 通知角色5
- **角色5**: 同步审查（队列优先级） → 反馈（问题分级）
- **角色6**: 审查通过后即时测试
- **角色8**: 全程收集问题/效率/习惯/Token/过程文档

### 阶段3: 集成测试
- **角色6**: 全量集成测试 → 回归测试

### 阶段4: 总结评估
- **角色7**: 质量门禁检查 → 交付确认 → 进化方案
- **角色8**: 同步到全局知识文件 → 确认过程文档完整

---

## 8条闭环反馈链路

```
①进化闭环:    角色7进化方案 → 知识库 → 下一轮读取 → 验证效果
②债务闭环:    记录债务 → 下一轮处理 → 验证 → 统计偿还率
③需求反馈:    角色2发现重大遗漏 → 回退角色1 → 复审 → 记录遗漏率
④变更闭环:    用户变更 → 角色1重新分析 → 角色2校验 → 回溯修改
⑤评估行动:    角色7评估发现异常 → 触发纠正 → 复评
⑥测试审查:    角色6编写用例 → 角色5审查 → 不合格修改 → 复审
⑦交付确认:    质量门禁全过 → 交付确认 → 不达标回退修复
⑧全局知识:    角色8全程收集 → 写入全局文件 → 检索复用 → 沉淀 → 迁移
```

## 关键规则

### 0.1 角色边界规范（新增 v3.3）
**每个角色必须严格遵守职责边界，禁止越权操作**：

| 角色 | 允许的操作 | 禁止的操作 |
|------|-----------|----------|
| **角色1 - 需求分析师** | ✅ 分析需求<br>✅ 拆解任务<br>✅ 时间预估<br>✅ 创建过程文档 | ❌ 编写代码<br>❌ 修改文件<br>❌ 执行命令 |
| **角色2 - 需求校验师** | ✅ 校验可行性<br>✅ 风险评估<br>✅ 查漏补缺 | ❌ 编写代码<br>❌ 修改文件<br>❌ 执行开发任务 |
| **角色3/4 - 开发工程师** | ✅ 编写代码<br>✅ 修改文件<br>✅ 执行命令<br>✅ 创建文档 | ❌ 需求分析<br>❌ 最终审查 |
| **角色5 - 代码审查师** | ✅ 审查代码<br>✅ 审查测试用例<br>✅ 提出改进建议 | ❌ 编写代码<br>❌ 修改功能逻辑 |
| **角色6 - 功能测试师** | ✅ 编写测试用例<br>✅ 执行测试<br>✅ 报告问题 | ❌ 修复 bug<br>❌ 修改代码 |
| **角色7 - 任务总结师** | ✅ 生成报告<br>✅ 质量评估<br>✅ 进化方案 | ❌ 编写代码<br>❌ 修改功能 |
| **角色8 - 知识收集师** | ✅ 更新全局知识<br>✅ 记录经验<br>✅ 打包迁移 | ❌ 编写业务代码<br>❌ 修改功能逻辑 |

**违反边界的后果**:
- 降低工作流程的可追溯性
- 混淆责任归属
- 影响质量控制

**正确做法**:
- 角色1/2 只负责分析和校验，输出文档
- 角色3/4 根据分析结果执行开发
- 角色5/6 独立审查和测试
- 角色7/8 最后总结和沉淀

### 0. 角色执行透明化（v3.2）
- **必须明确告知每个角色的执行状态**：✅完成 / ⏭️跳过 / ❌失败
- **如果跳过某个角色或任务，必须说明原因**，不能静默操作
- **必须追踪每个角色的进化情况**，记录能力提升和改进点
- **用户必须清楚知道**：
  - 哪些角色已执行
  - 哪些角色被跳过及原因
  - 整体流程的完成度
  - 角色能力的进化轨迹

示例输出格式：
```markdown
## 📊 SIRE 工作流执行状态

| 角色 | 状态 | 说明 |
|------|------|------|
| 角色1 - 需求分析师 | ✅ 完成 | 已拆解5个子需求 |
| 角色2 - 需求校验师 | ✅ 完成 | 发现2个遗漏点 |
| 角色3 - 开发工程师A | ✅ 完成 | 实现R001、R003 |
| 角色4 - 开发工程师B | ⏭️ 跳过 | R002-R006由角色3完成，无需并行 |
| 角色5 - 代码审查师 | ✅ 完成 | 审查通过，无重大问题 |
| 角色6 - 功能测试师 | ⏭️ 跳过 | 本次为设计阶段，无代码可测试 |
| 角色7 - 任务总结师 | ✅ 完成 | 生成执行报告 |

- 角色4: 当前任务规模较小，单开发者即可完成，无需并行开发
```

### 1. 触发条件
- **只有以 "sire" 开头的请求才会执行此工作流程**
- 非 "sire" 开头的请求按正常方式处理

### 2. 开发时间预估
- 每个需求必须预估开发时间
- **预估超过5分钟的任务必须向用户确认**：继续开发或拆解
- 拆解后子任务仍超5分钟需再次确认

### 3. 需求过程文档
- 每个需求从原始输入到完成，**必须生成并保存过程文档**
- 保存位置: `<SIRE_ROOT>/knowledge/global/projects/{项目名称}/docs/Rxxx_process.md`
- 必须包含10个固定章节（原始需求、拆解需求、校验结果、时间预估、执行信息、Token消耗、审查记录、测试记录、问题记录、最终状态）

### 4. Token统计
- 每个角色执行时记录输入/输出tokens
- 按需求编号归集
- 分4个阶段统计：需求分析、开发执行、审查、测试
- 汇总到过程文档第6节 + 全局开发效率纪要

### 5. 质量门禁（交付前必须全过）
1. 需求覆盖率 = 100%
2. 测试通过率 = 100%
3. 无 CRITICAL 级别未解决技术债务
4. 无 HIGH 级别未解决技术债务
5. 集成测试全部通过
6. 角色5审查全部通过
7. 争议全部已解决
8. 进化方案已写入进化知识库
9. 全局知识文件已更新（角色8确认）

### 6. 问题检索插队机制
- 任何角色遇到问题时，角色8 **最高优先级插队检索** 全局问题解决纪要
- 找到匹配方案 → 优先采用已有方案 → 复用次数+1
- 未找到 → 自行解决 → 解决后角色8记录新方案 → 形成知识沉淀

### 8. 过程日志记录规范（新增 v3.4）
**所有角色必须在执行过程中添加详细的过程日志，确保每一步操作都可追溯、可排查错误**。

#### 8.1 日志记录原则
- **宁可多记，不可遗漏**：每个关键步骤都必须有日志
- **结构化输出**：使用统一的日志格式
- **实时记录**：边执行边记录，不事后补记
- **用户可见**：重要日志必须向用户展示

#### 8.2 日志级别定义

| 级别 | 标识 | 使用场景 | 示例 |
|------|------|---------|------|
| INFO | ℹ️ | 正常流程节点 | "开始分析需求 R001" |
| DEBUG | 🔍 | 详细执行步骤 | "读取文件: src/main.py" |
| WARN | ⚠️ | 潜在风险 | "预估时间超过5分钟，需用户确认" |
| ERROR | ❌ | 执行失败 | "文件保存失败: 权限不足" |
| SUCCESS | ✅ | 成功完成 | "需求 R001 分析完成" |

#### 8.4 前端调试日志规范

**所有 API 调用必须添加 console.log 调试日志**：

```javascript
// 发送请求前
console.log('[DEBUG] 发送消息:', userMsg)
console.log('[DEBUG] 是否为文件生成请求:', isFileGenerationRequest(userMsg))
console.log('[DEBUG] 调用API类型:', isFileGen ? '/api/generate' : '/api/chat')

// 接收响应后
console.log('[DEBUG] /api/chat 请求内容:', message)
console.log('[DEBUG] /api/chat 响应:', response.data.response.substring(0, 100))
console.log('[DEBUG] 处理完成，耗时:', duration, 'ms')
```

#### 8.5 后端日志规范

**Python 后端必须使用 logger 记录关键操作**：

```python
logger.info(f"收到对话请求: {request.message[:50]}...")
logger.info(f"检测到文件操作需求，使用Agent模式处理")
logger.info(f"文件创建成功: {result.get('path')}")
logger.error(f"文件创建失败: {result.get('error')}")
logger.debug(f"意图识别结果: {intent}")
```

#### 8.6 日志输出位置

1. **控制台日志**：`console.log()` / `logger.info()` - 用于开发调试
2. **过程文档**：保存到 `Rxxx_process.md` 第5节「执行信息」
3. **全局效率纪要**：Token 统计、耗时统计汇总到 `global_dev_efficiency.md`

#### 8.7 错误排查日志模板

当发生错误时，必须记录以下信息：

```markdown
❌ [ERROR] {错误描述}
   - 操作: {正在执行的操作}
   - 文件: {涉及的文件路径}
   - 命令: {执行的命令}
   - 错误信息: {完整错误堆栈}
   - 上下文: {相关参数值}
   - 建议: {可能的解决方案}
```
