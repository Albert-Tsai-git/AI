### v3.10 原子 UNIT 与用户确认门禁（当前规则，覆盖旧版冲突项）

- R3 必须先按前端、后端、数据、验证等方向拆解，再继续拆成一个 UNIT 只含一个主要结果的最小可执行单元，例如“增加一个按钮”“增加一个方法”；每个单元必须有映射需求、负责人、依赖、具体写集、验收、验证、预估、风险和停止条件。
- R4 复核通过后，R0 必须把完整 UNIT 清单展示给用户，并将执行确认记为 `PENDING`；确认前 R5 不得进入 `READY` 或 `IN_PROGRESS`，不得执行代码、配置、文档或测试变更。
- 用户明确说出“不需确认”“自行完成”“直接执行”“按计划执行”等授权时，才允许使用 `approve-units --mode autonomous`，并记录用户原话；新增或修改任务列表后必须重新确认。
- 可用 `sire_run.py show-units` 随时重复查看清单，用 `approve-units --mode user-confirmed --note "用户确认以上任务列表"` 记录确认。

### v3.9 完整性监督、向量检索与迁移打包（当前规则，覆盖旧版冲突项）

- SIRE 角色扩展为 R0–R10；R9 是独立监督员，只维护关联内容清单、快照、差异分类、打包完整性和 STOP 信号，不修改业务、规则或知识正文；R10 是独立原生系统操作员，只执行已确认的系统/桌面应用 UNIT。
- 每个任务和实现单元进入执行前，R9 先运行 `sire_supervisor.py preflight`，R1 再运行 `sire_vector_db.py search`；每个单元前后都要执行 R9 检查。
- 发现关联内容缺失、移动、疑似被覆盖导致内容丢失或 zip 清单遗漏，立即 STOP、提醒用户，并排查分类为删除、覆盖/修改、移动、打包遗漏或其他原因；禁止自动重建或用新内容掩盖缺失。
- 仅当用户明确说出“打包工作流”时，R9 先验收，再运行 `sire_bundle.py`；未明确说出该短语时不得主动打包。打包必须包含全部历史 SIRE 产物和已有历史 zip，仅排除缓存、pyc 及本次正在生成的 zip/校验文件；完成后执行 `verify-zip --against-current`。
- 用户反对方向或计划时，先确认原因（已说明原因则直接记录），用 `sire_feedback.py` 保存原话、原计划、偏好、调整动作、阶段和标签。
- 所有角色严格遵守各自边界；越界必须停止并退回 R0 重新派工。未明确要求专门测试用例时，R7 只做基础验证；每个阶段/角色反馈一行写明“完成事项；隐患/阻塞”。
- 当前输出契约：每个阶段/角色必须返回核心产物；无需执行时必须显示“跳过”、原因和跳过记录，详细日志只写入 Run 目录。格式和最低产物以 `<SIRE_ROOT>/knowledge/global/SIRE-MIGRATION.md` 为准。
- 每次修改工作流内容后必须同步更新 `SIRE-MIGRATION.md` 的覆盖清单、版本和变更记录，未同步不得收尾。
- `sire_run.py init` 记录工作流控制文件指纹，`finish` 检查运行期间的工作流变更与迁移文档更新时间/哈希；检查失败必须阻止收尾。

## 概述

这是一个基于 **9个角色** 的自动化开发工作流程，通过分工协作、双开发者并行、交叉验证、完整性监督、测试左移、持续优化、全局知识沉淀和闭环反馈，确保软件开发的完整性、准确性和高质量。

### 核心特性

- **v3.1 新增角色8 - 全局知识收集师**：全程贯穿所有阶段，收集需求、问题、效率三类全局知识
- **问题检索插队机制**：任何角色遇到问题时，角色8优先检索全局是否有已解决记录
- **管理用户电脑上的个人全局知识文件**（跨项目持久）
- **提供设备迁移时的知识文件打包功能**
- **完全闭环体系**：7条闭环反馈链路 + 全局知识闭环

## 执行阶段

### 阶段1: 需求分析
- **角色1**: 读取进化知识库 → 分析需求 → 拆解 → 生成需求列表 → 时间预估
- **角色2**: 交叉对比 → 查漏补缺 → 生成最终需求清单
- **角色6**: 编写测试用例（角色2校验后）
- **角色5**: 审查测试用例质量
- **角色7**: 阶段1评估
- **角色8**: 创建过程文档（初始） → 收集需求内容

### 阶段1.5: 架构设计
- **角色3+角色4**: 协作制定技术方案
- **角色5**: 预审架构方案
- **角色7**: 阶段1.5评估

### 阶段2: 并行开发与审查闭环
- **角色3/角色4**: 并行开发 → 增量review → 通知角色5
- **角色5**: 同步审查（队列优先级） → 反馈（问题分级）
- **角色6**: 审查通过后即时测试
- **角色8**: 全程收集问题/效率/习惯/Token/过程文档

**⚠️ 强制要求：每个需求开发完成后，必须编写并执行测试用例，验证功能正常后才能继续下一个需求**

### 阶段3: 集成测试
- **角色6**: 全量集成测试 → 回归测试

### 阶段4: 总结评估
- **角色7**: 质量门禁检查 → 交付确认 → 进化方案
- **角色8**: 同步到全局知识文件 → 确认过程文档完整

## 8条闭环反馈链路

```
①进化闭环:    角色7进化方案 → 知识库 → 下一轮读取 → 验证效果
②债务闭环:    记录债务 → 下一轮处理 → 验证 → 统计偿还率
③需求反馈:    角色2发现重大遗漏 → 回退角色1 → 复审 → 记录遗漏率
④变更闭环:    用户变更 → 角色1重新分析 → 角色2校验 → 回溯修改
⑤评估行动:    角色7评估发现异常 → 触发纠正 → 复评
⑥测试审查:    角色6编写用例 → 角色5审查 → 不合格修改 → 复审
⑦交付确认:    质量门禁全过 → 交付确认 → 不达标回退修复
⑧全局知识:    角色8全程收集 → 写入全局文件 → 检索复用 → 沉淀 → 迁移
```

### 1. 触发条件

- **显式前缀触发**：消息去除前置空白后，以大小写不敏感的 `sire` 开头，且后接结束、空白、英文冒号、中文冒号或换行。

## 🔄 Skill 自我更新机制

### 自动版本管理
每次Skill更新时，必须执行以下步骤：

1. **版本号递增**
   - 主版本号：重大架构变更（v3 → v4）
   - 次版本号：新增功能或规范（v3.5 → v3.6）
   - 修订号：修复错误或优化描述（v3.6.0 → v3.6.1）

2. **更新元数据**
   ```yaml
   version: {新版本号}
   last_updated: {YYYY-MM-DD}
   ```

3. **记录变更日志**
   - 在「📝 Skill 变更日志」章节顶部添加新版本记录
   - 包含：版本号、日期、标题、更新内容列表、影响范围、向后兼容性

4. **通知用户**
   - 在更新完成后，向用户展示更新摘要
   - 提供查看完整变更日志的方法

### 更新示例

当需要添加新功能时：

```markdown
### v3.7 (2026-07-05) - 新增XXX功能
**更新内容**:
- ✅ 新增 X 节：XXX功能说明
- ✅ 修改 Y 节：优化ZZZ流程
- ✅ 修复 Z 节：解决AAA问题

**影响范围**: XXX模块  
**向后兼容**: ✅ 是 / ❌ 否（如不兼容，需说明迁移方案）
```

### 查看更新历史

用户可以通过以下方式查看Skill的更新历史：

1. **直接查看本文档**: 滚动到「📝 Skill 变更日志」部分
2. **查看版本号**: YAML frontmatter 中的 `version` 字段
3. **查看更新时间**: YAML frontmatter 中的 `last_updated` 字段
4. **Git历史**: `git log .qoder/skills/sire/skill.md`
5. **命令查询**: `sire 查看skill更新历史`

### 向后兼容性保证

- ✅ **向后兼容**: 旧版本的工作流仍然可用
- ⚠️ **部分兼容**: 某些功能可能需要调整
- ❌ **不兼容**: 需要手动迁移（会提供迁移指南）

每次更新都会在变更日志中明确标注兼容性状态。
