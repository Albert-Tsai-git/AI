### H-004: 硬件联调排查纪律 (来自 v3.4.6 力矩无响应排查)
**日期**: 2026-09-22
**项目**: driverSoftware (通用于上位机 + 固件联调)
**状态**: 生效
**关键词**: [排查纪律, 抓包, 真机测试, 固件档案, 签名同步, 波特率, 并行会话, 发布流程]

1. **先抓真实请求/回包, 再推理**: 浏览器 performance.getEntriesByType('resource') / read_network_requests 看有没有请求、返回码、响应体;
   preview 日志缓冲会被 hw_drain 刷满, 用 level=error 过滤直接看 Traceback。本案 500 的 TypeError 一眼就是根因。
2. **协议常量以固件头为唯一事实源**: 档案/刻度只能由生成器 (tools/gen_fw_profile.py) 产出, 手填必错; 并加"档案值 == 固件常量"的机械门禁。
   区分同名数值: 10000 是 Kp/Kd 量化 scale, 不是 pos/vel/tau 刻度。
3. **双实现接口改签名要两边同改**: 本仓 ReaderBackend 有 reader_mp (默认) 与 reader_wrapper 两份, 改一份必查另一份;
   用 inspect.signature 写测试钉住。
4. **总线参数单一真相源在后端连接状态**, 不信前端各自传的值 (前端 store 可能未同步, 回退默认值就静默错配)。
5. **真机测试要有安全兜底**: 小力矩 + 阻尼 (Kd) 限速, 每档限时, 出故障/温度越界即停, 结束必确认 kStopped;
   UI 自动化时用派发 keydown Enter 提交 (本页 blur 会回滚未提交输入), 不用 Tab。
6. **注意并行会话/他人提交**: 文件被莫名改回 (本案 17:36 档案回滚) 先查是否有别的会话在同仓工作;
   发版前必 fetch 对账 (本案远端多出同事修同一问题的 c8ad4e6, 需 rebase 取其版本)。
7. **发布按仓库流程**: CHANGELOG [未发布] 一句白话 → release.py <ver> (bump/截断/tag) → 分别推 development 与 tag →
   git ls-remote 核 tag 指向; 正式包由 CI Runner 构建, 本地不手传。发完回收缺陷池"待发布"占位。
8. **结论前先证伪**: 读一个寄存器就能否定的假设 (如 0x89 自动清除) 不要写进结论; 报告时把"已证实"与"推测"分开。


### H-005: 按任务复杂度和验收风险选择模型以控制成本

**日期**: 2026-10-12
**项目**: Codex SIRE shared workflow
**关键词**: 模型选择, 低成本模型, token 成本, 复杂度分级, task routing, model escalation

**需求场景 / 现象**: 用户要求智能体先判断每个任务单元的复杂度与执行风险，选择相称的模型，降低简单工作的 token 成本，同时保持验收质量。

**方案 / 架构**: 沿用共享契约已有的模型选择门禁，不固定某个型号为永久规则。简单检索、机械修改和现成检查等易核验、低影响工作优先使用当时可用的低成本模型；常规实现按工作复杂度选择适当档位；需要设计取舍、复杂排错、高风险决策及最终裁决留给高档模型。极小任务不为派工而增加代理开销。选择时一并考虑上下文切换、返工成本和错误影响；首次低档执行未通过验收时，逐级升级模型。

**关键文件与接口**:
- `workflow/shared/sire/references/global-contract.md` — 已有 R4 后模型门禁、难度分级及升级规则，本记录只归档用户稳定偏好。
- `scripts/sire_paths.py` — 解析 Claude/Codex 共用知识库和 SQLite 路径。

**实施步骤**:
1. 对任务单元按复杂度、影响、可核验性和返工成本选择模型。
2. 在 run 台账注明实际模型及理由；记录升级或验收结果。
3. 将常态偏好与本次实际执行所用模型分开记录，型号随当前可用选项而变化。

**验证方法**: 本次 U1 为低难度、机械归档单元，R4 已批准复用既有规则；实际由 `gpt-6-luna low` 执行。本型号只作为本次事实，不代表长期固定偏好。

**踩坑**: 首次 Markdown 检索传入不存在的回执目录，脚本未记录回执；随后在正确 run 目录重跑并成功记录。归档前通过历史配置与只读检查确认 `D:\sire\sire_vectors.sqlite3` 是既有机器级 SIRE 共用运行库。

**状态**: 已完成

### H-007: 用户说提供tag时：按仓库规则只给tag，不做提交

**日期**: 2026-10-19
**项目**: 通用（所有仓库）
**状态**: 生效
**关键词**: [提供tag, 打tag, 发tag, 仓库tag规则, 不提交, 不推送代码]

用户说"提供/给我一个 tag"时：

1. **只提供 tag，不做提交**：不 `git add`/`commit`/`push` 代码，不顺手跑门禁、不改任何文件。
2. **按该仓库自己的 tag 规则命名**：先读仓库文档（AGENTS.md / CLAUDE.md / docs/branching.md 等）确认通道和格式，查远端已有 tag 取下一个编号，只给出 tag 名（以及建好后的推送命令），不自作主张用 `dev-xxx` 之类的临时名。
3. **是否创建、推送 tag 由用户另行指示**；用户没说"推"就只给名字。用户随后给出确定的 tag 名，以用户给的为准。

**来由**: 2026-10-19 EncoderPlotter 中，用户说"提交代码，然后 push，提供给我一个 tag"，我先擅自推了不合规的 `dev-median-check-outer`，被纠正后又改推 `test-v4.10.0-88-…`，用户明确要求以后"提供 tag"只提供、不做提交。

**需求场景 / 现象**: 用户要 tag 时，助手把"提供"理解成"提交+推送+建 tag"，越权操作并用了不合规的 tag 名。

**方案 / 架构**: 见上 1~3 条；tag 命名取自仓库规则（本仓为 `test-vX.Y.Z-NN[-描述]`，NN 取远端最大编号+1）。

**验证方法**: 用户说"提供 tag"后，只输出 tag 名/命令，`git status`、远端 tag 列表均无新增。

### H-009: 改 CI 脚本先本地测试好再提交推送，不要把 pipeline 当调试循环

**日期**: 2026-11-05
**项目**: quality-testing/dv3-admin
**状态**: 生效
**关键词**: [CI, 流水线, 本地测试, 推送, pipeline, 调试循环, 提交信息]

用户原话要求“本地测试好再提代码，不要在 pipeline 里面测试”。起因是排查 deploy 阶段时连续推送了多次，每次都触发完整打包和上传。做法：能在本机复现的部分（PowerShell 片段、YAML 语法、ACL 操作、变量注入解析）先本地跑通；本地无法覆盖的部分明确告诉用户，由用户决定是否推送，不自行连续推送迭代，推送前仍需用户确认。用户事后明确说“多测试几次打包和部署”时，才可在授权范围内多次触发流水线，优先用手动触发同一提交的方式，不为触发而新增提交。技术约束另见 P-20261105：该仓库的提交信息用英文。
